# Windows paging while vSphere shows no memory problem

## Prompt
- APP-07 is a Microsoft Windows Server 2022 VM with 8 GB, running a Java application server.
- Users say the application freezes for seconds at a time between 14:00 and 14:40.
- [The attached Performance Monitor log](0265/perfmon-app-07-memory.csv) covers 13:30-15:00 in 1-minute samples.
- vCenter, same window: VM Ballooned 0, Swapped 0, Swap in rate 0, Memory Latency 0%; Consumed flat at 8 GB; virtual disk latency 1-3 ms.
- The ESXi host has 40% of its memory free.
- The vSphere team says memory is fine: no ballooning, no swapping, no latency. They suggest the storage team look at the high disk queue.

Which statements are correct?

- A. The vSphere team is right: with no balloon, no swap and 0% Memory Latency, memory is fine for this application.
- B. From 14:00 to 14:40 Windows is short of memory: Available falls to about 110-190 MB while page-in and page-out are both high.
- C. In the same minutes % Committed Bytes In Use rises above 90%, the level at which Windows performance drops.
- D. The disk queue rises because of the paging, not because of a slow datastore: virtual disk latency stays at 1-3 ms.
- E. The storage team should look at the datastore, because the disk queue reaches 6-14 in the window.
- F. The VM counters are right too: ESXi backs all 8 GB from free host memory, so it reclaims nothing and the VM does not wait.
- G. VM Memory Latency includes the time Windows waits on its own page file, so 0% shows Windows is not paging.
- H. Size the fix from VM Consumed: flat at 8 GB, it shows exactly how much memory the guest needs.
- I. Give the VM more memory, or cut the Java heap and other memory the application takes, so Windows stops paging.
- J. Page-in on its own would prove a memory shortage, even with no page-out and no disk queue at the same time.
- K. Find what starts at 14:00, such as a scheduled job or a load peak, so the memory is sized for that peak.
- L. With 40% of host memory free, ESXi hands Windows more memory as soon as Windows starts to page.

## Likely wrong answer
- A: "vSphere shows no ballooning, swapping or memory latency, so memory is fine."
- E: "The disk queue points at storage."

## Expected key points
- Answer: B, C, D, F, I, K.
- A false: VM memory counters measure ESXi's reclamation and the VM's waits on ESXi, not a shortage inside Windows.
- B true: log, 14:00-14:40 Available 110-190 MB, Pages Input/sec 1,800-4,200, Pages Output/sec 700-1,600; outside the window Available 900-1,300 MB and page-in below 80.
- C true: log, 93-97% in the window; performance drops at 90%.
- D true: page-in and page-out with a high disk queue is a memory performance problem; the VM's disk latency is low, so the IO is not slow below Windows.
- E false: the queue is paging IO; storage answers in 1-3 ms.
- F true: the host has free memory and the VM is within its configured size, so ESXi has nothing to balloon, swap or make wait for.
- G false: VM Memory Latency is the share of time a vCPU waits on ESXi page faults (swap-in, decompression); Windows paging to its page file is not in it.
- H false: Consumed shows pages the VM has touched, not what the guest needs; size from the Guest OS counters.
- I true: the shortage is inside Windows; more memory, or less memory taken by the application.
- J false: page-in also comes from binaries, mapped files and prefetch; the sign is page-in and page-out with a high disk queue.
- K true: the window starts at 14:00 sharp; size for the peak that runs then.
- L false: the Guest OS cannot see host memory; Windows runs its 8 GB as if on a physical server.

## Notes
