# Performance Monitor: queue on a 4-vCPU VM

## Prompt
- The owner of the 4-vCPU Windows Server VM batch-win-04 says the nightly batch runs slowly and asks for 4 more vCPUs.
- He sends [the typeperf export of the batch hour](0434/typeperf-cpu.csv), 1-minute samples from 01:00 to 02:00.

Which statements are correct?

- A. A Processor Queue Length sustained above about 2 per vCPU shows threads waiting for a processor.
- B. Threads already executing on a vCPU are part of the Processor Queue Length values.
- C. Rising Context Switches/sec values are reason enough to add vCPUs.
- D. With all 4 vCPUs near 100% and a long queue, the batch wants more CPU time than Windows gets.
- E. Check the VM's CPU Ready and Co-stop for the same hour before adding vCPUs.
- F. Four more vCPUs are the fix: a queue above 2 per vCPU shows the batch is short of processors.
- G. vCenter shows the VM's CPU Usage at the same value as Windows % Processor Time.
- H. With all four processors this busy, the queue length adds nothing to the diagnosis.
- I. The Processor Queue Length is at 0 for most of the hour.
- J. % Processor Utility above 100% shows vCPUs running above nominal frequency, not more busy vCPUs.

## Answers
A, D, E, J

## Explanation
- A true: reading. `System\Processor Queue Length` is above 8 (2 per vCPU) in at least 50 of the 60 rows. Windows excludes running threads from the queue, so a queue sustained above about 2 per processor means threads wait for a processor (MSDN reads above 2 sustained as congestion).
- B false: Windows counts threads in the Ready, Standby and Deferred Ready states; running threads are not in the queue (Linux counts them).
- C false: the misconception. A high or rising switch rate is not a CPU shortage on its own; the queue is the counter to read, and more vCPUs can raise switching.
- D true: reading. `Processor(0)` to `Processor(3)` `% Processor Time` are at 90 or above in at least 54 of the 60 rows, with the long queue of A: the workload demands more runtime than the Guest OS gets.
- E true: a vCPU waiting for a physical thread is invisible to Windows; Ready and Co-stop show whether the VM got the runtime it asked for, and more vCPUs on a busy host can raise them.
- F false: the wrong action. The Guest OS view alone does not settle it; VM contention comes first.
- G false: the two are measured in different layers. Windows CPU usage ignores the host's Hyper-Threading; VM CPU Usage, measured by the VMkernel, accounts for it (for example 62.5% for a Windows vCPU at 100% on a shared core).
- H false: the over-correction. Busy processors alone do not show that threads wait; the queue is the primary Guest OS counter for whether the CPU keeps up.
- I false: reading. The queue is 0 in no row; it stays above 8 for most of the hour.
- J true: Windows 8 and later report usage above 100% when the processor runs above its nominal frequency (Turbo); in the export `% Processor Utility` passes 100 in most rows (it is `% Processor Time` scaled by the frequency ratio), while `% Processor Time` cannot pass 100.
- Misconception: F: the queue read as proof that more vCPUs are needed, without the VM's view. Or C: the context switch rate read as a CPU shortage.
