# CPU usage dropped after a downsize

## Prompt
- VM erp-app-05 was downsized from 16 to 8 vCPUs in the vSphere Client on Wednesday, 4 November, before the working day. Its CPU shares are at the default. Its host is esx-07, with a 2.5 GHz nominal clock.
- [The attached export](0236/erp-app-05-busy-hour-before-after.csv) shows the busiest hour of each working day, 7 days before and 7 days after the change.
- The application owner: "CPU usage dropped from about 9.6 GHz to 8.5 GHz since you took my vCPUs. The application is starved. Give the 8 vCPUs back."

Is the owner right? What happened, and what do you change?

## Likely wrong answer
"Yes: usage fell after the downsize, so the VM now has too few vCPUs: add them back."

## Expected key points
- Partly: since the change the VM gets about 1.2 GHz less than it demands, but not because 8 vCPUs are too few. CPU Demand stayed at about 9.3-9.8 GHz before and after: the workload is the same.
- Guest OS peak CPU queue stayed at 2-4 before and after: threads inside the guest are not waiting for a vCPU.
- Usage per vCPU rose from about 24% to about 43%: the same work on half the vCPUs, as expected.
- The gap is Ready: below 0.5% before, 5-6.5% after. Usage fell about 1.2 GHz below Demand, which is the time the VM waited for a physical thread.
- Why: default CPU shares are per vCPU, so the VM went from 16,000 to 8,000 shares. On a host near 80-86% utilization in the busy hour, the smaller VM is entitled to less under contention.
- Fix: raise the VM's CPU shares (or move it to a less busy host), not the vCPU count. Then check that Ready falls back and Usage meets Demand.

## Notes
- Drafted 2026-11-12.
- Default shares: 1,000 per vCPU at Normal; resizing in the vSphere Client recalculates them (vSphere 9.1 Resource Management, Shares).
- Also acceptable as a next check: the load on the VM's NUMA home node on esx-07.
- CSV generated by a seeded script; Demand 9.31-9.83 GHz, Ready before 0.28-0.40%, after 5.26-6.48%.
