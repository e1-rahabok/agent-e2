# Web applications slow on Monday morning

## Prompt
- DRS cluster prod-cl02: 6 hosts (esx-01 to esx-06), each 16 cores at 2.0 GHz (32 GHz). DRS fully automated, vSphere HA on. Two resource pools at the root: RP-Web (30 VMs) and RP-Batch (8 VMs).
- Sunday's change window included change CHG-4471: "Cap the batch jobs: CPU limit of 40 GHz on the batch resource pool. Implemented by script."
- Monday from 08:30, users of every web application report slow pages. The batch team reports no problem.
- The infrastructure manager wants to add two hosts before noon.
- Attachments, Monday 08:30-09:30, from VCF Operations:
  - [the VM export](0239/vms-monday-0830-0930.csv): per VM, its pool and host, the busy-hour averages of CPU Ready, Co-stop, Usage, Memory Contention, Balloon and virtual disk latency;
  - [the pool and host export](0239/pools-and-hosts-monday-0830-0930.csv): every 5 minutes, the CPU usage of each pool (MHz) and of each host (% of its 32 GHz).

Which statements are correct?

- A. The most likely cause is a 40 GHz CPU limit on RP-Web, not on RP-Batch: CHG-4471 hit the wrong pool.
- B. RP-Web CPU usage sits flat at about 39.8-40.0 GHz in every 5-minute sample, which is the shape of a ceiling.
- C. RP-Batch varies between about 28.6 and 32.7 GHz, so nothing in the data shows it held at 40 GHz.
- D. The batch jobs take CPU from the web VMs: a limit on RP-Batch starves its sibling pool.
- E. Many VMs show high CPU Ready, so the cluster is short of CPU and the two hosts are needed.
- F. Every host runs at about 30-48% of its CPU, so the cluster is not short of CPU capacity.
- G. Web VMs show 9-18% Ready on every host, batch VMs on the same hosts below 1%: the wait follows the pool, not the host.
- H. A pool limit applies across the cluster, so a web VM on a quiet host is held back by the load of web VMs on other hosts.
- I. Memory Contention near 0 on every VM, web and batch alike, rules memory out as the cause of the slowness.
- J. batch-03's 3 GB of balloon shows its host is short of memory now, so memory is a second cause.
- K. web-17's virtual disk latency of about 9 ms explains the slow pages across all the web applications.
- L. CPU Ready leaves out the time a vCPU is held back by a limit; a limit shows only as lower Usage.
- M. More vCPUs on the web VMs would give them more CPU, because each added vCPU brings its own entitlement.
- N. Once the limit is off RP-Web, web VM Ready falls and RP-Web usage leaves its flat line at 40 GHz.
- O. Setting RP-Web's CPU shares to High lifts its VMs' CPU while the limit stays in place.

## Likely wrong answer
- D: "The batch jobs take the CPU from the web VMs."
- E: "Many VMs show high CPU Ready, so the cluster is short of CPU: add the two hosts."

## Expected key points
- Answer: A, B, C, F, G, H, I, N.
- A is correct: the pool the change was meant for runs below the limit and the other pool sits flat at it: the change hit the wrong pool.
- B is correct: export, RP-Web 39,815-40,007 MHz, flat sample after sample near a round number.
- C is correct: export, RP-Batch 28,566-32,694 MHz; it varies with its load.
- D is wrong: a limit caps only its own pool and frees CPU for the siblings; it cannot raise Ready in another pool.
- E is wrong: Ready confined to one pool, with spare host CPU, is a limit. Check pool and VM limits first.
- F is correct: export, hosts at 29.9-47.6% of 32 GHz.
- G is correct: export, web VMs 9.2-17.9% Ready, batch VMs 0.8% at most, on the same hosts.
- H is correct: a pool's limit is cluster-wide while each VM runs on one host.
- I is correct: export, Memory Contention 0.00-0.19% on every VM.
- J is wrong: Balloon is memory reclaimed earlier; batch-03 shows Memory Contention 0, so it does not wait now.
- K is wrong: one VM at about 9 ms cannot explain slow pages on every web application; the other web VMs sit at 1-4 ms.
- L is wrong: Ready includes the time held back by a limit (the limbo queue); that is the web VMs' Ready here.
- M is wrong: more vCPUs share the same 40 GHz pool limit.
- N is correct: the hosts have spare CPU (30-48%), so without the limit the web VMs get their demand: the check of the fix is web VM Ready falling and the pool's usage no longer flat at the limit.
- O is wrong: shares act only under contention and never lift a limit; with spare host CPU the cap, not the share, holds the web VMs.

## Notes
- Synthetic, 2026-11-12, the second long scenario.
- CSVs generated by a seeded script: RP-Web 39,815-40,007 MHz; RP-Batch 28,566-32,694 MHz; the VM usage of each pool sums to its pool mean (39,939 and 30,122 MHz); host usage is the sum of its VMs plus about 3% for the kernel, 30-48% of 32 GHz; web VMs Ready 9.2-17.9%, batch VMs 0.8% at most.
- A limit on a resource pool applies across the cluster (vSphere 9.1 Resource Management, Resource Pool Attributes). Ready includes limit time.
- Option J does not say where batch-03's balloon came from; a memory limit balloons first (resource-controls, Limit), and J stays false either way: Memory Contention 0 means no current wait.
- 2026-11-15 audit: old M (Max Limited) dropped, as the VM-limit pair 0103/0066 keeps the limit-time fact; old O (the remedy) reworded to the check, as 0066/0103 keep the remedy; O added (raise RP-Web's shares, false). Letters: A-L unchanged; M dropped; N -> M; O -> N (reworded); O new.
