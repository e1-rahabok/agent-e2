# esxtop shows memory overcommit on a quiet host

## Prompt
- A new administrator opens esxtop on the ESXi 9.1 host esx-m3-05 and sees memory overcommit above 0.
- They raise a ticket: the host is short of memory and its VMs will soon swap. They plan to vMotion VMs off the host until the overcommit reads 0.
- The memory panel header, as they pasted it into the ticket:

```text
3:07:44pm up 112 days 06:40, 1311 worlds, 38 VMs, 164 vCPUs; MEM overcommit avg: 0.41, 0.40, 0.39
PMEM  /MB: 786234   total:  2907     vmk,359600 other, 423727 free
VMKMEM/MB: 785898 managed:  8476 minfree, 19077 rsvd, 766821 ursvd,  high state
PSHARE/MB:    5006  shared,    1286  common:    3720 saving
SWAP  /MB:       0    curr,       0 rclmtgt:                 0.00 r/s,   0.00 w/s
ZIP   /MB:       0  zipped,       0   saved
MEMCTL/MB:       0    curr,       0  target,  215760 max
```

Which statements are correct?

- A. For each 1 GB that ESXi manages, about 1.4 GB is requested.
- B. The VMs on this host are short of memory right now, as the ticket says.
- C. The rclmtgt of 0 on the SWAP line shows that ESXi has no target to swap memory now.
- D. MEMCTL, SWAP and ZIP at 0 show nothing ballooned, swapped or compressed now.
- E. The PSHARE saving above 0 shows that the host already reclaims memory under pressure.
- F. Host swapping cannot start on this host while the overcommit stays below 1.
- G. Keep moving VMs off the host until esxtop shows no overcommit at all.
- H. The three values close together show a steady overcommit over the last 15 minutes.
- I. The VMKMEM line of the header shows the host in the soft memory state right now.

## Answers
A, C, D, H

## Explanation
- A is correct: MEM overcommit avg is requested over managed memory, minus 1; the three values are 0.39 to 0.41, so requested is about 1.4 times managed.
- B is wrong: requested counts configured memory, not touched memory. VMKMEM reads `high state`, PMEM free is far above minfree, and SWAP, ZIP and MEMCTL are 0: no shortage.
- C is correct: rclmtgt is the target in MB that ESXi sets for swapping; 0 means it plans to swap nothing, consistent with the high state.
- D is correct: MEMCTL curr, SWAP curr and ZIP zipped are the host sums of ballooned, swapped and compressed VM memory; all read 0.
- E is wrong: page sharing runs all the time, whatever the memory state; the other reclamation mechanisms start as pressure rises, and the header shows high state with nothing ballooned, compressed or swapped.
- F is wrong: over-correction. Any overcommit above 0 means the VMs may touch more than the host has; then ESXi moves through ballooning and compression to host swapping, which slows the VMs that touch swapped pages.
- G is wrong: the wrong action. Overcommit above 0 is planned; migrate on contention (VM memory latency, swap-in), not on this line.
- H is correct: the values are exponentially weighted averages with 1-, 5- and 15-minute windows; the three are within 0.05 of each other: a steady overcommit.
- I is wrong: the reading. The VMKMEM line ends with `high state`.
- Misconception: B: "Overcommit above 0 means the host is short of memory and will swap." Or E: page sharing read as reclamation under pressure.
