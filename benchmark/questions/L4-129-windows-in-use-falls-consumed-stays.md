# Windows In use falls after a restart; VM Consumed stays

## Prompt
- The Windows Server 2022 VM jas-prod-03 has 32 GB of memory and runs a Java application server. At 15:02 UTC its owner restarted the application to free memory.
- The owner sends [the typeperf export from the guest](0386/typeperf-memory.csv), 5-minute samples from 12:00 to 18:00 UTC.
- You export [the vCenter memory chart of the VM](0386/vcenter-vm-memory-past-day.csv), Past day, cut to the same six hours. vCenter keeps statistics at level 2 for all intervals.
- The owner writes: "Windows gave the memory back, but vCenter did not notice. Either vCenter is broken, or the VM leaks. And if vCenter is right, the VM is short of memory."

Which statements are correct?

- A. Windows In Use is lower after the restart than before it by at least a quarter of the VM's memory.
- B. In the vCenter export, Consumed drops at about the time of the restart.
- C. After the restart, Windows keeps the freed pages on its own lists, which ESXi has no view of.
- D. ESXi keeps a VM page mapped once the guest has touched it, so Consumed has no reason to fall.
- E. The level Consumed values show vCenter lagging behind Windows; a later collection will catch up.
- F. Active in the vCenter export is the VM-side copy of Windows In Use.
- G. A leak inside Windows is what holds Consumed up after the restart.
- H. The VM needs more memory, because Consumed sits close to its configured size.
- I. With the Windows counters at hand, the Consumed values of this VM can be ignored for every purpose.
- J. Whether this VM needs more memory is read from Windows counters, part of the cache included.

## Likely wrong answer
E: "vCenter is just behind; Consumed will follow Windows down." Or F: "The VM counter for In Use is Active." Or A rejected because `% Committed Bytes In Use` hardly moves across the restart.

## Expected key points
- Answer: A, C, D, J.
- A is correct: reading. In Use = total - (Modified + Standby + Free), and `Available MBytes` is Standby plus Free, so In Use moves by minus the change of `Available MBytes` plus `Modified Page List Bytes`. That sum is at least 9,224 MB higher in every row from 15:05 than in any row up to 15:00 (16,866 MB at least after, 7,641 MB at most before): In Use fell by more than 8 GB, a quarter of 32 GB. `Committed Bytes` and `% Committed Bytes In Use` stay within a few percent, because the restarted JVM commits its heap again at start without touching it; commit is not In Use.
- B is wrong: reading. `Consumed for jas-prod-03` stays between 32,780,000 and 32,880,000 KB (about 98% of 32 GB) in every row, with no step at 15:05.
- C is correct: freeing a page only updates the guest's free list, an ordinary memory write that never reaches ESXi. How Windows classifies its pages (the rise of `Free & Zero Page List Bytes` here) is an ESXi blind spot.
- D is correct: ESXi maps a VM page at the guest's first touch and keeps the mapping until it reclaims the page (sharing, balloon, compression, swap). `Ballooned memory`, `Swapped` and `Compressed` are 0 in every row: nothing is reclaimed, so Consumed stays near the configured size, and the restarted application reuses pages already mapped.
- E is wrong: there is no mapping between In Use and Consumed; the layers manage memory independently, so waiting does not make them agree.
- F is wrong: the same mistake on another counter. Active is a sampled ESXi estimate of recently touched pages; it has no mapping to In Use.
- G is wrong: Consumed is not the guest's utilization; it stays high once pages are touched. The fall in In Use shows that Windows released the memory.
- H is wrong: the wrong action. Consumed near the configured size is the normal state of a VM that has touched its memory; it is not demand.
- I is wrong: over-correction. Consumed shows the host memory the VM holds: what host capacity and the VM's footprint (for example, for a migration) count.
- J is correct: Guest OS sizing reads the guest's own counters, with part of the cache; VM counters describe what ESXi does.
