# Linux load average far above the vCPU count

## Prompt
- A Linux VM with 8 vCPUs runs a database replica. Reports run slowly every morning from 09:40.
- `uptime` at 09:50 shows load average: 31.8, 29.5, 22.1.
- [The attached vmstat output](0260/vmstat-10s-db-replica-02.csv) covers 09:40-09:50 (`vmstat -t 10`, memory in KiB).
- vCenter, VM real-time charts, same window:
  - CPU Ready: 0.6% per vCPU. Co-stop: 0.
  - Data disk (scsi0:1): read latency about 38 ms, write latency about 6 ms, about 1,850 read IOPS.
- The application team proposes going from 8 to 16 vCPUs.

Which statements are correct?

- A. The load average is about four times the vCPU count, so the CPU is saturated; 16 vCPUs would halve the load per vCPU.
- B. Linux load average counts runnable tasks and tasks in uninterruptible sleep; here most of it is the `b` column, tasks blocked on IO.
- C. The `r` column stays below 8, so threads are not queuing for a vCPU.
- D. Linux waits on IO while the VM's data disk shows high read latency, so the wait sits below Linux: continue with that virtual disk and its datastore.
- E. `wa` is CPU time spent processing IO; add it to `us` and `sy` to get the real CPU busy figure.
- F. A Linux load average of 31.8 means the same as an esxtop load average of 31.8: demand for about 32 times the CPUs present.

## Likely wrong answer
A: load average above the vCPU count read as CPU saturation, so more vCPUs. Or E: iowait counted as busy CPU.

## Expected key points
- Answer: B, C, D.
- A is wrong: the load is mostly blocked tasks (`b` about 25-34) while `id` stays near 40%. More vCPUs do not make the disk answer faster.
- B is correct: Linux load average includes tasks in state D (uninterruptible sleep, usually waiting for IO). That is why it can exceed the vCPU count with idle vCPUs.
- C is correct: `r` (runnable, including running) stays at 1-5, below the 8 vCPUs.
- D is correct: wait high inside Linux and VM disk latency high at the same time places the wait below Linux, in the VM's storage path. If VM latency were low, the wait would sit in the Linux IO stack instead.
- E is wrong: `wa` is idle time while IO is outstanding. The vCPU could run other work.
- F is wrong: esxtop load average counts running and ready worlds against the physical CPUs (1.00 = all PCPUs busy). Linux load average is not normalised and includes tasks waiting for IO. Same name, other object.

## Notes
- CSV generated by a seeded script: `r` 1-5, `b` 25-34 (mean `r` + `b` about 32, matching the 1-minute load average), `id` about 40%, `wa` 44-52%, `si`, `so` and `st` 0, `bi` about 15,000 KiB/s (about 1,850 reads of 8 KiB).
- Load average definition: Linux kernel documentation, /proc/loadavg (proc(5)): runnable and uninterruptible tasks.
