# Input types

## Inputs and outputs
- Six input types feed alerts, dashboards and reports: metric, property, event (with task), log, trace, NetFlow. Each has its own purpose and format, and they overlap.
- Outputs: live screen, alert and report are pushed; a dashboard is pulled.
- An alert is not an input, although work starts from it. It is a trigger defined on inputs: a log event occurs, a property changes, a metric crosses a threshold.
- Which input feeds which output:
  - metric → live screen, alert, report, dashboard;
  - event and task → alert, dashboard;
  - property → report, dashboard;
  - log, trace, NetFlow → dashboard.
- Inputs derive from each other: log, event, trace and NetFlow can yield metrics; a log can yield an event; a metric crossing a threshold yields an event; a property change is an event.

## Metric
- Produced at a regular interval, even when the value is constant. So a state (powered on, connected) is a metric, not a property.
- Generated by the system. A user does not enter or edit it.
- Always a number at origin. It may be shown as a string for reading.
- The number can be a code with a string meaning: -1 for a limit means no limit.
- Raw or computed. A computed metric derives from metrics and properties: a super metric in VCF Operations.
- Three classes: contention, consumption, context.
- Crossing a threshold can raise an event or write a log message. Counting events gives a metric: number of vMotions in a cluster.
- A daily trend across hundreds of clusters can show a problem before it happens, so no alert is raised at all.

## Property
- Changes when something is configured, not at a predictable interval.
- Number of VMs in a cluster: a metric, even if it does not change for years. It is the result of activity, not a setting.
- Maximum number of VMs in a cluster: a property; it is part of the cluster's capability.
- Number of ESXi hosts in a cluster: a property; the cluster is configured with them. Number of running ESXi hosts: a metric.
- A property change is an event and can raise an alert. Its weight depends on which property changed; not every property matters.

## Event
- A record of something that happened: bad, neutral or good; planned or unplanned. Bad ones may warrant an alert.
- Not at a regular interval.
- Has a start time and may have an end time. A threshold crossed starts an event; the value falling back below ends it.
- Change events: a setting change, a state change, or a label change.
  - State change: DRS on a cluster goes from disabled to enabled.
  - Setting change: the DRS migration threshold goes from 2 to 5; the automation level stays Fully Automated.
  - Label change: a tag marks the cluster for decommissioning. A label is external, not an inherent property of the object; no setting or state changes.
- Activity events record actor, target, activity and time: an administrator enabled DRS on a cluster at a given date and time.

## Log
- A raw message, usually written by developers.
- Numbers in it can be extracted as metrics; text can describe an event. Metrics and events can then raise alerts.
- More than 99.9% of log lines are not useful. The design question is cost against benefit.

## Trace and NetFlow
- Needed in some situations, beyond the four basic inputs.
- Trace: a record of code in motion. Some traces yield metrics. Used for function-level troubleshooting.
- NetFlow: the path taken by network flows. Shows networked relationships and yields metrics.

## Traps
- "Power state is a property because it rarely changes" → it is sampled at a regular interval, so it is a metric.
- "Number of VMs in the cluster is a property because it has been constant for months" → it results from activity and is collected every interval: a metric. The maximum number of VMs is the property.
- "Number of hosts in the cluster is a metric" → configured hosts is a property; running hosts is a metric.
- "Alerts are an input to monitoring" → an alert is an output: a trigger defined on metrics, properties, events or logs.
- "A limit of -1 is a negative limit" → -1 is a code for no limit.
- "Collect every log line for analysis" → almost all log lines are not useful; extract the metrics and events that matter and weigh the cost.
