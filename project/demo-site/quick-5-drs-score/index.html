Quick answer · cluster prod-cl02
Cluster prod-cl02: 10 hosts, 420 powered-on VMs, DRS fully automated, default migration threshold. The Cluster DRS Score is 92%, steady all morning. Since 09:00 the owners of the VM pay-db-01 report slow queries. My team lead says the DRS score is high, so the cluster is fine and the problem must be inside the database. Is that a valid conclusion?
Agent E2

No. A Cluster DRS Score of 92% does not validate that prod-cl02 is free of performance problems and it does not rule out pay-db-01 as the source of slow queries.

Cluster DRS Score is a weighted average of VM DRS Scores, a measure of execution efficiency / VM happiness, not contention. Performance Best Practices 9.1 says >80% means no performance impact, but a good cluster score can hide a few VMs with low scores; the VM list under Monitor > vSphere DRS sorts VMs by score lowest first. Cluster metrics are averages; one suffering VM is hidden and low cluster utilization does not rule out VM contention. Performance is unmet demand per consumer.

ESXi CPU Demand is a sum-of-consumers metric: sum of VMs’ ideal demand with no contention, with no reservation. It is a capacity metric, not a performance signal. Demand above Usage can be reservation alone, so read VM CPU Ready and Co-stop for contention.

VM CPU Co-stop applies only to multi-vCPU VMs. A vCPU that gets ahead of a sibling that is Ready is stopped to keep vCPUs close in progress; the co-stopped vCPUs stop even when threads are free. Co-stop tends to be smaller than Ready and is typically <1% in high-performing environments.

What to check next for pay-db-01 since 09:00: VirtualMachine Peak CPU Ready among any vCPU % 20s, Peak CPU Co-stop % 20s, Peak memory wait %, Peak read/write latency among vDisks ms; Cluster worst peak vCPU Ready/Co-stop/memory wait/disk latency and Cluster Performance % depth/breadth; VM limits/shares/resource pool, DRS blockers and placement. Guest OS counters are needed to settle whether the database itself is the cause.

Assumption: pay-db-01 is multi-vCPU, so Co-stop is applicable.
