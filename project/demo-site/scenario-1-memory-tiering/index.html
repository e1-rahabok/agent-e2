Scenario 1. A bank payments cluster on VCF 9.1.1 with memory tiering. Two correct changes by two teams, then a long weekend. Risk (potential) warned on Wednesday and Friday; contention (actual) hit on Tuesday. The L2 specialist on call knows neither change. Agent E2 answers from its knowledge base only; every answer below is unedited output of the Agent E2 pipeline.

The trap

  • L1: "1.6 TB consumed on 1 TB hosts, we are swapping."
  • Capacity: "Memory Capacity Remaining was 38%."
  • DBA: "Our SQL VMs show no wait."
  • VM Performance (%) 99 and Cluster Performance (%) 96: green.

Every one of them is right about its own number, and every one points away from the cause.

The cause

  • CHG-1 turned memory tiering off on 6 SQL VMs and reserved all their memory: each takes 256 GB of DRAM away from the tiered VMs on its host.
  • CHG-2 added 40 VMs, approved on a capacity number that counts NVMe as DRAM.
  • The long weekend let idle pages go cold. On Tuesday the working set no longer fits the DRAM left: the VMs wait on NVMe.

What Agent E2 must show

  • Contention against consumption against context, read together (Triple See).
  • The NVMe wait that memory contention does not count.
  • A sustained read, not a warm-up, against the August baseline.
  • The Cluster Risk rows that stepped up on Tuesday night and Thursday night: the clue to two changes the specialist never saw.

The week

  1. Mon: Normal. Memory tiering on since June; active memory 45% of DRAM.
  2. Tue 22:00-23:30: CHG-1, DBA team, blueprint SQL Gold v3: sql-pay-01 to 06 (16 vCPU, 256 GB) powered off, sched.mem.enableTiering = FALSE, all memory reserved, powered on. Broadcom guidance for SQL. Seen by the DBA team only.

  4. Thu 21:00-23:40: CHG-2, application team: 40 VMs (8 vCPU, 32 GB) moved in, approved on Memory Capacity Remaining 38%. Seen by the application and capacity teams.
  5. Fri: Fine for users. Cluster Risk: active memory leaves green (52.7%), NVMe latency turns yellow. Cluster Performance 98. Nobody looks.
  6. Sat-Mon: National Day long weekend. Idle pages go cold and move to NVMe.

The root cause of the latency is memory tiering contention (NVMe wait) on the hosts of CL-SG-PRD-PAY, specifically triggered by a "warm-up" period following the National Day long weekend.

Mechanism and Reason

The L1 compute's premise that the system is swapping is wrong. "Highest ESXi DRAM Memory Consumed" of 157% is a design feature of memory tiering, where pages exceed DRAM and reside in NVMe [vsphere/object-types/cluster/models/cluster-risk]. The metrics prove there is no swapping or ballooning (both 0), so there is no "swap-in" contention [vsphere/technology/memory/metrics/virtual-motherboard/swapped].

The latency is caused by NVMe wait. On esxi-pay-05, the NVMe read bandwidth is high (380 MBps) and NVMe read latency has spiked to 290 µs. This is a classic "warm-up" scenario: after the long weekend, pages that went cold and moved to NVMe are being fetched back into DRAM [vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host]. The "Worst memory wait" of 5.8% confirms this is the primary performance hit, as it sums memory latency and NVMe wait [vsphere/object-types/cluster/cluster-performance].

What to check next

  1. Wait for warm-up: Compare current NVMe read bandwidth against values from the previous business day to see if it is falling.
  2. Check NVMe device health: Run esxcli nvme device log smart get to ensure the latency is not due to hardware wear [vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host].
  3. Verify Tiering exclusion: Confirm if any high-priority VMs should have tiering disabled via full memory reservations [vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host].

CHG-2 caused the latency. No, do not roll back CHG-2.

Mechanism and Reason

CHG-1 disabled tiering and added full reservations for six SQL VMs (6 x 256 GB = 1.536 TB). Because full reservations for non-tiered VMs shrink the DRAM available for other VMs (vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host), the effective DRAM:NVMe ratio for the rest of the cluster fell significantly.

CHG-2 then added 40 VMs (40 x 32 GB = 1.28 TB). While the cluster had "Capacity Remaining" (which counts total usable capacity, including the NVMe tier), it did not have enough DRAM. This forced more pages of the tiered VMs into the NVMe tier, as seen in the "Highest ESXi DRAM Memory Consumed" rising from 121% to 157% and "Memory Tiering Consumption" increasing from 21% to 44% [vsphere/object-types/cluster/models/cluster-risk, vsphere/object-types/cluster/models/cluster-consumption].

The latency occurred on Tuesday because the working set of these VMs now exceeds the reduced DRAM. Following the long weekend, a "warm-up" happened: pages that moved to NVMe were fetched back, causing high NVMe read bandwidth (380 MBps) and NVMe wait (Worst memory wait 5.8%) [vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host, vsphere/object-types/cluster/cluster-performance].
