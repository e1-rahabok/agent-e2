Scenario 1. The payments application servers wait for memory pages stored on NVMe, because the hosts that also run a SQL VM no longer have enough DRAM for the application's working set. Two changes on the same payments service, by two teams, made that happen, and a long weekend exposed it. The L2 specialist on call knows neither change. Agent E2 finds the facts and analyses them; the L2 specialist decides the fix. Every answer below is unedited output of the Agent E2 pipeline, answering from its knowledge base.

The service

  • The payments service has a database tier, sql-pay-01 to 06, already in cluster CL-SG-PRD-PAY.
  • Its application tier, 40 VMs (pay-api and pay-web), ran on an old cluster until this week.
  • The cluster has 8 identical hosts, each with 1 TB of DRAM and a 1 TB NVMe memory tier. Memory tiering has been configured since June, but DRAM consumed never passed 80%, so no page had ever moved to NVMe.

The cause

  • CHG-1 (DBA team) turned memory tiering off on the 6 SQL VMs and reserved all their memory: 256 GB of each host's DRAM now belongs to one SQL VM.
  • CHG-2 (application team) moved the 40 application VMs in, approved on a capacity number that counts NVMe as DRAM. On Friday DRAM consumed passed 80%, and tiering started for the first time.
  • Over the long weekend idle application pages moved to NVMe. On Tuesday the application needs them back, and its working set no longer fits the DRAM left.

What Agent E2 must show

  • Contention, consumption and context, read together (Triple See).
  • The NVMe wait that Memory Contention does not count, behind a VM Performance of 17.
  • Why now: tiering started on Friday, and the weekend moved the pages.
  • The Cluster Risk rise on Wednesday and Friday: the clue to two changes the specialist never saw.
  • Facts and analysis only: the fix is the L2 specialist's decision.

The week

  1. Mon: Normal. DRAM consumed 68% on the worst host. NVMe consumed 0. Cluster Risk 22.5 (green).
  2. Tue 22:00-23:30: CHG-1, DBA team, blueprint SQL Gold v3: sql-pay-01 to 06 (16 vCPU, 256 GB) powered off, sched.mem.enableTiering = FALSE, all memory reserved, powered on. Seen by the DBA team only.
  3. Wed: Fine for users. The memory reservation sub-metric of Cluster Risk goes from 0 to 26%; Cluster Risk 25.5 (yellow). Level 1 does not act on yellow.
  4. Thu 21:00-23:40: CHG-2, application team: the 40 payments application VMs (8 vCPU, 32 GB) move in to sit next to their databases, approved on Memory Capacity Remaining 38%. Five land on esxi-pay-05, next to sql-pay-03. Seen by the application and capacity teams.
  5. Fri: The application goes live and consumes memory. On esxi-pay-05, DRAM consumed passes 80% at 08:40, so tiering starts for the first time: new pages go to NVMe. Cluster Risk 31.1 (yellow). Cluster Performance 98; users fine. Level 1 does not act on yellow.
  6. Fri 18:00 to Mon: National Day long weekend; load near zero. DRAM is above 80%, so idle pages move to NVMe: NVMe writes up, NVMe consumed 50 → 280 GB. NVMe reads stay near 0, because nobody touches those pages.
  7. Tue 09:05: Business resumes. The application touches its pages and they come back from NVMe. Payments API p99 latency from 180 ms to 1.4 s. Service desk.
  8. Tue 10:20: The L2 vSphere specialist is called: not part of either change, and the change calendar is not open to them yet.

Assumption: "slow" means the tiered VMs on esxi-pay-05, and the same pattern on other hosts is unverified. The cause is a working set that no longer fits DRAM on esxi-pay-05, so tiered VMs wait on NVMe fetches. Act now by moving load off that host.

Mechanism

  • Active memory is 790 GB, 77% of DRAM. Above 75% means significant loss is expected (is-memory-tiering-slowing-host, step 2).
  • NVMe reads stayed high an hour apart (380 then 360 MBps). That is a sustained working set beyond DRAM, not a weekend warm-up (step 3).
  • NVMe read latency of 290 µs is in the "potential issues" band (step 4).
  • sql-pay-03's full 256 GB reservation shrinks the DRAM left for the 34 tiered VMs (step 7). That explains why pay-05 is worse than pay-07 and pay-08, which hold no SQL VM.

Premises that fail

  • pay-api-07's 0.2% Memory Contention does not rule out tiering. That counter is unaware of NVMe fetches. Its NVMe wait is 6 × 256 × 0.00029 ÷ 8 = 5.57% (cluster-performance), which matches VM Performance at 17%.
  • "Capacity Remaining (%)" invites reading it as capacity free now. It is really a 3-Day Forecast Capacity Remaining (%) from last Wednesday, taken before the Thursday change. The KB does not say whether it reads active memory against DRAM. Cluster Risk at 66% is the current reading (cluster-risk).
  • The DBA's "no wait" fits a VM with a full reservation. It does not clear sql-pay-03's effect on its neighbours.

Do now

  1. Rank the VMs on esxi-pay-05 by NVMe read bandwidth (step 5).
  2. vMotion the heaviest readers to esxi-pay-07 and esxi-pay-08, after confirming their DRAM headroom.
  3. Check the active memory of hosts 01–04 and 06 before using them.

Check next

  • The change calendar for Tue 23:25 and Thu 23:35.
  • Migration history.
  • The teller app VMs' hosts.

Conclusion

esxi-pay-05 is throttling pay-api-07 because its working set (77% Active) exceeds DRAM, forcing sustained NVMe fetches. The 5.57% NVMe wait (calculated from 6 MB/s and 290 µs latency) drives the VM Performance drop to 17%.

Mechanism

The new file confirms that ESXi Memory Latency is a normalized average that hides the specific VM suffering. Therefore, the low host-level signal is irrelevant; the metric to trust is the worst VM's contention. Here, the "wait" is not traditional page-fault latency (which is unaware of tiering) but the NVMe wait component added to the KPI. The 380 MB/s read rate is not a transient warm-up because Active Memory remains high at 77%, indicating the working set genuinely does not fit in DRAM.

What to check next

  1. Immediate mitigation: Migrate pay-api-07 off esxi-pay-05 to a host with lower Active Memory (e.g., esxi-pay-07 at 44%) to escape the NVMe latency penalty.
  2. Verify DRS: Check why DRS did not move the VM earlier. If DRS is blocked by affinity rules or data locality, migrate manually.
  3. Long-term fix: Since the working set exceeds DRAM on this host, either add DRAM to esxi-pay-05 or permanently move the heavy SQL VMs (which have tiering off) to hosts with sufficient headroom to keep tiered VMs' Active Memory below 75% of DRAM.

The root cause is memory tiering slowing the VM pay-api-07. The VM is experiencing a "warm-up" period after the long weekend, where cold pages moved to the NVMe tier are being fetched back into DRAM, causing vCPU freezes.

Mechanism and Reason:

  1. Host Saturation: esxi-pay-05 is under memory pressure. DRAM consumption passed 80% on Friday (vsphere/object-types/cluster/models/cluster-consumption), triggering memory tiering. By Tuesday, DRAM Consumed reached 108% and Active Memory rose to 77% of DRAM, which is the signal for significant performance loss on tiered hosts (vsphere/technology/memory/concepts/memory-tiering).
  2. NVMe Fetch Wait: The VM pay-api-07 has a Memory Contention (Latency) of 0.2%, which is low because that counter is unaware of memory tiering (vsphere/technology/memory/metrics/virtual-motherboard/latency). However, it is reading from NVMe at 6 MB/s.
  3. Calculation: Using the NVMe wait formula (vsphere/object-types/cluster/cluster-performance):

6 MB/s × 256 pages/MB × 0.00029 s (latency) ÷ 8 vCPUs × 100 = 5.58\%.

This 5.58% vCPU wait is the primary driver of the VM Performance score (17%) and the application latency.

  1. Context: The pattern of near-zero reads until Tuesday morning, followed by a spike, is a classic "warm-up" after an idle period (National Day weekend) (vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host).

What to check next:

Monitor the NVMe read bandwidth for pay-api-07 over the next hour. If it falls, it was a warm-up; if it stays high, the working set no longer fits in DRAM (vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host).
