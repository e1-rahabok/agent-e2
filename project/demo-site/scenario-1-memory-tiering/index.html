Scenario 1. The payments application servers wait for memory pages stored on NVMe, because the hosts that also run a SQL VM no longer have enough DRAM for the application's working set. Two changes on the same payments service, by two teams, made that happen, and a long weekend exposed it. The L2 specialist on call knows neither change. Agent E2 finds the facts and analyses them; the L2 specialist decides the fix. Every answer below is unedited output of the Agent E2 pipeline, answering from its knowledge base.

The service

  • The payments service has a database tier, sql-pay-01 to 06, already in cluster CL-SG-PRD-PAY.
  • Its application tier, 40 VMs (pay-api and pay-web), ran on an old cluster until this week.
  • The cluster has 8 identical hosts, each with 1 TB of DRAM and a 1 TB NVMe memory tier. Memory tiering has been configured since June, but DRAM consumed never passed 80%, so no page had ever moved to NVMe.

The cause

  • CHG-1 (DBA team) turned memory tiering off on the 6 SQL VMs and reserved all their memory: 256 GB of each host's DRAM now belongs to one SQL VM.
  • CHG-2 (application team) moved the 40 application VMs in, approved on a capacity number that counts NVMe as DRAM. On Friday DRAM consumed passed 80%, and tiering started for the first time.
  • Over the long weekend idle application pages moved to NVMe. On Tuesday the application needs them back, and its working set no longer fits the DRAM left.

What Agent E2 must show

  • Contention, consumption and context, read together (Triple See).
  • The NVMe wait that Memory Contention does not count, behind a VM Performance of 17.
  • Why now: tiering started on Friday, and the weekend moved the pages.
  • The Cluster Risk rise on Wednesday and Friday: the clue to two changes the specialist never saw.
  • Facts and analysis only: the fix is the L2 specialist's decision.

The week

  1. Mon: Normal. DRAM consumed 68% on the worst host. NVMe consumed 0. Cluster Risk 22.5 (green).
  2. Tue 22:00-23:30: CHG-1, DBA team, blueprint SQL Gold v3: sql-pay-01 to 06 (16 vCPU, 256 GB) powered off, sched.mem.enableTiering = FALSE, all memory reserved, powered on. Seen by the DBA team only.
  3. Wed: Fine for users. The memory reservation sub-metric of Cluster Risk goes from 0 to 26%; Cluster Risk 25.5 (yellow). Level 1 does not act on yellow.
  4. Thu 21:00-23:40: CHG-2, application team: the 40 payments application VMs (8 vCPU, 32 GB) move in to sit next to their databases, approved on Memory Capacity Remaining 38%. Five land on esxi-pay-05, next to sql-pay-03. Seen by the application and capacity teams.
  5. Fri: The application goes live and consumes memory. On esxi-pay-05, DRAM consumed passes 80% at 08:40, so tiering starts for the first time: new pages go to NVMe. Cluster Risk 31.1 (yellow). Cluster Performance 98; users fine. Level 1 does not act on yellow.
  6. Fri 18:00 to Mon: National Day long weekend; load near zero. DRAM is above 80%, so idle pages move to NVMe: NVMe writes up, NVMe consumed 50 → 280 GB. NVMe reads stay near 0, because nobody touches those pages.
  7. Tue 09:05: Business resumes. The application touches its pages and they come back from NVMe. Payments API p99 latency from 180 ms to 1.4 s. Service desk.
  8. Tue 10:20: The L2 vSphere specialist is called: not part of either change, and the change calendar is not open to them yet.

Cluster CL-SG-PRD-PAY is slowed by memory tiering on esxi-pay-05, not by generic capacity. The working set no longer fits the DRAM left on the host.

Mechanism

  • Memory tiering capacity is Active memory vs DRAM, not Consumed vs total. Worst ESXi Active Memory is 77 % of DRAM today vs 34-46 % Mon-Wed, and Highest ESXi DRAM Memory Consumed is 108 % – >100 % because the tier is counted in Consumed. vsphere/technology/memory/metrics/virtual-motherboard/active
  • Over the 3-day National Day weekend the host was idle: NVMe write bandwidth rose Friday 18:00 → Tuesday 08:00, NVMe consumed 0 → 280 GB, NVMe read bandwidth ~0. Pages went cold to NVMe.
  • Tuesday 09:10/10:15 NVMe read bandwidth is 380 / 360 MB/s sustained for 65 min, >200 MB/s threshold, with NVMe read latency ~290 µs. The decision tree step 3 flags sustained >200 MB/s as “working set no longer fits the DRAM left”. vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host
  • Effective DRAM is reduced by the non-tiered SQL VM. sql-pay-03 is 256 GB reserved, tiering off, active 110 GB on esxi-pay-05. A full reservation is a guarantee and cannot be overcommitted; admission control counts reservations, never usage. vsphere/architecture/resource-controls The reservation plus the active working set of the 34 tiered VMs pushes Active to 790 GB ≈ 77 % of 1 TB DRAM, so tier fetches are unavoidable.

Cluster Risk 66 %, Cluster Performance 48 % and the 09:05 latency spike line up with the NVMe wait burst. pay-api-07 shows VM Performance 17 % with 6 MB/s NVMe read, Memory Contention 0.2 % – the wait is tier-induced, not classic memory contention.

What to do now

  • Immediate relief: evacuate the non-tiered reserved VM. vMotion sql-pay-03 off esxi-pay-05 to esxi-pay-07/08 which have Active 44/41 % of DRAM and only ~30 MB/s NVMe read. That frees ~256 GB of reserved DRAM for the tiered workload.
  • Meanwhile move the hottest tiered VMs off esxi-pay-05; start with the VMs contributing to the 380 MB/s NVMe read. Check per-VM NVMe read bandwidth memstats -r vmtier-stats and migrate to the cool hosts.
  • Keep ballooned/compressed/swapped at 0 – they are not the cause; NVMe wait is. Do not add memory or change tier size now; monitor NVMe read bandwidth for 1 hour after moves to confirm it falls <200 MB/s and latency drops.

The root cause is memory tiering contention on host esxi-pay-05. The Payments API is slow because its working set no longer fits in the remaining DRAM, forcing sustained fetches from the NVMe tier.

Mechanism and Reason

  1. Working Set Shift: After the 3-day weekend, the working set of the VMs on esxi-pay-05 shifted. The host's active memory rose to 77% of DRAM, and NVMe consumed increased to 280 GB.
  2. Sustained NVMe Reads: The NVMe read bandwidth is sustained above 200 MBps (380 MBps at 09:10 and 360 MBps at 10:15), which indicates the working set no longer fits in the DRAM left (flow row flow-esxi-nvme-read-sustained).
  3. VM-Level Impact: While pay-api-07 has low Memory Contention (0.2%) and CPU Ready (0.8%), these counters are unaware of memory tiering (vsphere/technology/memory/vm-memory-latency-high). The VM is waiting for pages fetched from NVMe.
  4. Wait Calculation: Using the formula from vsphere/object-types/cluster/cluster-performance, pay-api-07's NVMe wait is: 6 MB/s × 256 pages/MB × 0.00029 s ÷ 8 vCPUs × 100 = 5.57%. This contributes to the poor VM Performance (17%) and Cluster Performance (48%).
  5. DRAM Pressure: The presence of sql-pay-03 (256 GB reserved, tiering off) reduces the DRAM available for other tiered VMs, exacerbating the pressure on the NVMe tier.

What to check next

Check the NVMe read bandwidth of other VMs on esxi-pay-05 to identify if multiple VMs are contending for the NVMe tier.

Immediate Corrective Action

vMotion some tiered VMs off esxi-pay-05 to other hosts (e.g., esxi-pay-07 or 08) to reduce the active memory demand on that host's DRAM.

What the run taught us

  • Run once per model, best first (the round of 2026-11-16): Muse Glimmer 30B, then Gemma 31B. Neither passes: both score 4.5 of 7, so the run stopped there. No frontier model: it is not what ships.
  • What the new code fixed: both answers now call the reads sustained, from the computed fact Agent E2 gives them (flow-esxi-nvme-read-sustained, step 3). Before it, Gemma called the same reads a warm-up.
  • What both get right: active memory at 77% of DRAM, the SQL VM with tiering off taking DRAM from the tiered VMs, and the room on esxi-pay-07 and esxi-pay-08. Gemma computes the NVMe wait (5.57%) behind the VM Performance of 17.
  • What both miss: the symptom start times (Tue 23:25, Thu 23:35, Fri 08:40) as dated changes, the clue the scenario is built on, and the flaw in Capacity Remaining on a tiered cluster, although its note reaches them through the term map. Neither explains that tiering started only on Friday, when DRAM consumed passed 80%.
  • Muse lost its case: its first step (reading the question) was cut at 2,400 tokens because its reasoning tokens count toward the limit (plan, M3a).
  • Muse proposes remedies (move sql-pay-03, move the hottest VMs): Agent E2 should stop at facts and analysis. The answer prompt does not say so yet.
  • Not settled by the knowledge base: whether an NVMe wait of about 5.6% alone explains a p99 of 1.4 s (Guest OS and application counters), and why DRS did not rebalance.
