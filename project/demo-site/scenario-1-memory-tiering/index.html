Root cause, written by the specialist

Three unrelated changes over one week.

  • Change 1 took 25% of each host's DRAM out of the tiering pool. DRAM consumption passed 80%, so tiering ran from then.
  • Changes 2 and 3 made other VMs active while the payments VMs sat idle over the holiday, so the payments pages went to NVMe.
  • On Tuesday at 09:05 the payments VMs touched those pages and waited for each fetch from NVMe. By 09:55 their working set was back in DRAM.

Why it was not caught: Cluster Risk went up 9 days ago but was ignored: there was no actual performance problem, and cluster capacity looked healthy (Memory Capacity Remaining counts NVMe as DRAM). Saturday's insight touched many payments VMs, but the VMs are not grouped, so VCF Operations had no information that they belong to one application.

Not the cause: memory tiering worked as designed. No hardware fault.

Fix, proposed by the specialist

Remediation

  • Cap ESXi memory reservation at 10% of DRAM, from 25%. Reserving 25% of DRAM costs both capacity and performance: memory tiering has at most 75% left, and the hypervisor needs memory too. Cluster Risk flags it correctly: its memory reservation row is yellow from 10%.
  • Applications sensitive to memory tiering warm up their cache on a schedule. Iterating through application buffers, database buffer pools or in-memory caches touches the pages on NVMe, and ESXi fetches them back into DRAM.

Future detection

  • A VM alert based on application grouping, to catch a problem across many VMs of one application.
  • The daily SOP includes the breadth of VMs with pages on NVMe.

Discussion with upper management

  • Infrastructure needs to be application-aware. Group the VMs in the vCenter folder hierarchy, and reflect the application structure in the folders and a VCF Operations custom property.

Next: the review with the DBA, application and security teams; each fix is theirs to decide.

The VM waited on NVMe tier fetches, not on CPU Ready or reclaimed-page memory contention, and disk latency is not indicated by the data provided.

VM Performance % in VCF Operations is a KPI from contention sub-metrics: Peak CPU Ready, Peak CPU Co-stop, Memory wait – which on tiered hosts is VM mem|20_sec_peak_host_contentionPct plus NVMe wait – Peak disk latency and Peak network TX drops. The peak is 20-second, not 5-minute.

For pay-api-01 at 09:15:

  • Peak CPU Ready 0.9% and peak Memory Contention 0.2% are near zero; Ballooned, Compressed and Swapped are 0. VM Memory Latency is the reclamation wait, swap-in and decompression, and it excludes balloon. It is unaware of memory tiering.
  • NVMe read bandwidth is 12 MBps at 09:15 vs 0 before 09:05. Host esx-sg01-14 NVMe read latency is 210 µs at 09:15.

On a tiered host Memory Latency does not count NVMe fetches. NVMe wait is computed from the VM’s NVMe read bandwidth and host NVMe read latency. With 8 vCPUs:

NVMe wait ≈ 12 MBps × 256 pages/MB × 210 µs / 8 ≈ 8.1% of vCPU time.

That wait feeds the Memory wait component of VM Performance and explains the drop from 99% to 17% at 09:15 while CPU Ready and Memory Contention stayed near zero. ESXi Memory Latency is a normalized average of VM Memory Latency and hides the victim; it is not used for alerting or troubleshooting.

VM Disk Latency is a primary performance counter for VM Performance, but no disk latency value is provided and NVMe read bandwidth is a memory-tier signal, not a virtual-disk signal.

Conclusion: the VM’s pages were cold and demoted to NVMe over the 3-day public holiday while the host stayed above the ~80 % DRAM start point for tiering, and the wait stopped on Tuesday morning once the workload restarted, the working set became hot again and the pages were fetched back from NVMe to DRAM.

Mechanism and reason

  • Memory tiering is active on the host. Tiering starts when host DRAM consumption reaches about 80 %: from then new memory is allocated from NVMe. vsphere/technology/memory/concepts/memory-tiering
  • With tiering, frequently accessed data stays on DRAM, infrequently accessed data is placed on the NVMe tier. Pages are classified by recency and frequency; hot pages are those accessed most often in about the past minute; the rest are cold. vsphere/technology/memory/concepts/memory-tiering
  • A page on NVMe is fetched back to DRAM when it becomes active; the vCPU that touched it waits for the fetch. The fetch shows as NVMe read bandwidth, which counts pages fetched from NVMe when they become active; NVMe write bandwidth counts cold pages moved down. vsphere/technology/memory/concepts/memory-tiering
  • Active is an estimate of pages touched recently. On a host with memory tiering it is the capacity limit: host active memory against DRAM decides whether tiering slows the VMs. vsphere/technology/memory/metrics/virtual-motherboard/active

Active is a rate reported as space, rises fast and falls slowly, ESXi estimates the working set by statistical sampling over a period of 60 s by default, smoothed over several periods. vsphere/technology/memory/metrics/virtual-motherboard/active

Why pages were on NVMe Tuesday morning

Host esx-sg01-14 DRAM consumption has been above 80 % since Sunday 9 days ago, so tiering is on and new allocations go to NVMe.

During the holiday the VM was idle: active memory fell to ~0.3 GB Saturday-Sunday-Monday, Tuesday 08:55 0.4 GB. The VM’s working set was cold, so the tiering classification moved its pages down. NVMe consumed grew from 0.4 GB Friday 15:00 → 10 GB Saturday 18:00 → 19 GB Sunday 08:00 → 20 GB Tuesday 08:55 while NVMe read bandwidth was 0 Friday to Tuesday 09:05. Cold pages were demoted in the background, no fetches were needed.

Why the wait appeared at 09:15 and stopped by 09:55

Tuesday is the first business day. At 09:15 the VM active memory jumps from 0.4 GB at 08:55 to 12 GB, then 11 GB at 09:55. The working set became hot again, so pages that were on NVMe had to be brought back.

NVMe read bandwidth is 12 MBps at 09:15 and drops to 0.3 MBps at 09:55, matching the NVMe consumed drop 20 GB → 13 GB → 3 GB. The reads are the fetches back to DRAM; the vCPU waits for each fetch. Once the hot set is resident in DRAM, fetches cease and the wait stops.

Decision-tree signal: NVMe consumed >0 confirms tiering is active; active memory as % of host DRAM is the leading signal, and NVMe read bandwidth >0 with per-VM reads identifies the VMs that wait on NVMe. vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host

What to check next

  • Confirm the exact workload restart time Tuesday morning and correlate with the active memory rise and NVMe read burst.
  • Per-VM NVMe read bandwidth and host NVMe read latency to quantify NVMe wait = VM NVMe read bandwidth ×256 pages/MB × host NVMe read latency ÷ vCPUs ×100. vsphere/object-types/cluster/cluster-performance
  • Host active memory vs DRAM to ensure active stays below the recommended ≤50 % of DRAM; at 50-75 % tiering is at risk. vsphere/technology/memory/concepts/memory-tiering
  • Ensure the VM is not excluded from tiering with a missing full reservation, and check reclamation metrics ballooned/compressed/swapped for configuration issues on a tiered host. vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host

Exact time of VM workload restart on Tuesday, Guest OS memory pressure details, VM swap usage, and host memory tiering policy thresholds and eviction behavior specific to this VCF 9.1.1 build.

  • The 256 GB reservation is sticky and counts for admission control as set, not as touched. Host memory reservation went 0% → 25% of DRAM since Sunday 9 days ago 02:10, matching the VM’s 256 GB reservation.   • A memory reservation is a guarantee, not use. Pages are held only after they are touched and then stay with the VM. The VM’s active memory is 110 GB, so ~110 GB of the 256 GB is already touched and pinned in DRAM. vsphere/architecture/resource-controls
