Root cause, written by the specialist

Three unrelated changes over one week.

  • Change 1 took 25% of each host's DRAM out of the tiering pool. DRAM consumption passed 80%, so tiering ran from then.
  • Changes 2 and 3 made other VMs active while the payments VMs sat idle over the holiday, so the payments pages went to NVMe.
  • On Tuesday at 09:05 the payments VMs touched those pages and waited for each fetch from NVMe. By 09:55 their working set was back in DRAM.

Why it was not caught: Cluster Risk went up 9 days ago but was ignored: there was no actual performance problem, and cluster capacity looked healthy (Memory Capacity Remaining counts NVMe as DRAM). Saturday's insight touched many payments VMs, but the VMs are not grouped, so VCF Operations had no information that they belong to one application.

Not the cause: memory tiering worked as designed. No hardware fault.

Fix, proposed by the specialist

Remediation

  • Cap ESXi memory reservation at 10% of DRAM, from 25%. Reserving 25% of DRAM costs both capacity and performance: memory tiering has at most 75% left, and the hypervisor needs memory too. Cluster Risk flags it correctly: its memory reservation row is yellow from 10%.
  • Applications sensitive to memory tiering warm up their cache on a schedule. Iterating through application buffers, database buffer pools or in-memory caches touches the pages on NVMe, and ESXi fetches them back into DRAM.

Future detection

  • A VM alert based on application grouping, to catch a problem across many VMs of one application.
  • The daily SOP includes the breadth of VMs with pages on NVMe.

Discussion with upper management

  • Infrastructure needs to be application-aware. Group the VMs in the vCenter folder hierarchy, and reflect the application structure in the folders and a VCF Operations custom property.

Next: the review with the DBA, application and security teams; each fix is theirs to decide.

Conclusion: pay-api-01 waited on NVMe fetches from the memory tier at ~09:15, not on CPU or reclaimed memory. That explains the VM Performance drop to 17 % with CPU Ready peak 0.9 % and Memory Contention peak 0.2 %.

Mechanism and reason

  • VM Performance % is the VM contention KPI. It aggregates peak CPU contention, memory wait and the other contention rows. CPU Ready is near zero and Memory Contention is near zero, balloon/compressed/swapped are zero, so CPU and reclaimed-memory waits are absent.
  • The host is memory-tiered. VM Memory Latency / VCF Operations Memory Contention is the share of vCPU time waiting for page faults: swap-in and decompression, not balloon, and it is unaware of memory tiering. On a tiered host NVMe fetches are a separate memory wait that Latency does not count.
  • At 09:15 VM NVMe read bandwidth is 12 MB/s and host NVMe read latency is 210 µs. With 8 vCPUs Little’s law gives ~8.1 % of vCPU time spent waiting on NVMe. That wait is not in Memory Contention, so the KPI falls while the two memory/CPU counters stay green. Before 09:05 and after 09:55 NVMe bandwidth is 0 MB/s and VM Performance returns to 99 %.

What to check next

  • Per-VM NVMe read bandwidth around 09:00-10:00 and host NVMe read rate/latency to confirm a cold-page burst.
  • Host active memory % of DRAM and which working set became active at 09:15.

Payments VMs pages were demoted to NVMe by normal memory tiering because the host was tiering-active and their working set was cold.

Host esx-sg01-14 has 1:1 DRAM:NVMe and tiering configured. Host DRAM consumption has been >80% since Sunday 9 days ago. Memory tiering starts when host DRAM consumption passes about 80%: from then new memory is allocated from NVMe and the classification module ages pages by recency/frequency, keeping hot pages in DRAM and moving cold pages to NVMe. NVMe write bandwidth is demotion – cold pages moved down in the background off the vCPU’s path. vsphere/technology/memory/concepts/memory-tiering

Active memory is the capacity constraint on a tiered host: host active memory against DRAM decides whether tiering slows VMs. Active is an estimate of pages touched recently. vsphere/technology/memory/metrics/virtual-motherboard/active

  • Payments VMs active memory 0.3 GB each Saturday-Monday → their pages are cold.
  • Load-test VMs active memory 4 GB →150 GB Saturday 10:00-18:00.
  • 32 other VMs active memory 120 GB →260 GB Sunday 01:00-07:00.

The two bursts raise host active memory. With host active memory rising against a DRAM pool that is already >80% consumed, tiering reclaims DRAM by demoting cold pages from all tiered VMs. Host NVMe write bandwidth matches the bursts: <5 MBps Friday, up to 140 MBps Saturday 10:00-18:00, up to 160 MBps Sunday 01:00-07:00, while host NVMe read bandwidth stays <5 MBps Saturday-Monday. Pages are written down but not read back.

Hence payments VMs, idle with essentially no active pages, are the first to be aged out. Their NVMe consumed grows 1 GB →30 GB Saturday 18:00 →58 GB Sunday 08:00 →60 GB Tuesday 08:55, while host NVMe consumed grows 35 GB →120 GB →190 GB →190 GB. No NVMe reads are needed because the VMs stay idle.

Next to check: per-VM tier1Consumed/memstats -r vmtier-stats for the three payments VMs to confirm demotion, and verify sched.mem.enableTiering is not FALSE for them; tiering off would need a full reservation otherwise pages go to host swap.

Conclusion: crm-db-03 with tiering off and a full 256 GB reservation removes 256 GB of DRAM from the pool that tiered VMs can use and forces the host to start tiering earlier. That is the expected effect, not a fault.

Mechanism and reason

  • A VM with sched.mem.enableTiering = "FALSE" is excluded from tiering. To stay in DRAM it must have a full memory reservation; otherwise it competes for DRAM and its pages go to the host swap file. vsphere/technology/memory/concepts/memory-tiering
  • A memory reservation is a guarantee that admission control counts, whether used or not, and once touched pages stay with the VM. Reservation consumed counts VMs only and follows the setting. vsphere/architecture/resource-controls ; vsphere/technology/memory/metrics/host/reservation
  • Tiering starts when host DRAM consumption passes about 80%. The capacity constraint on a tiered host moves from Consumed to Active memory: Active must stay within DRAM, ideally <50%. vsphere/technology/memory/concepts/memory-tiering ; vsphere/technology/memory/metrics/virtual-motherboard/active
  • With tiering off the VM’s 256 GB reservation is DRAM-only. On 1,024 GB DRAM that is 25 % of DRAM reserved and no longer reclaimable for tiered VMs. Effective DRAM left for tiered VMs falls, so the DRAM:NVMe ratio drops below the configured 1:1. Example given in the KB: two 200 GB fully reserved excluded VMs on 1 TB DRAM + 1 TB NVMe leave the remaining VMs at ~0.6:1. vsphere/technology/memory/concepts/memory-tiering

What you see on esx-sg01-14

Host memory reservation % of DRAM went from 0 to 25 % at Sunday 02:10, exactly the 256 GB reservation. Host DRAM consumption rose from ~74 % to 81-84 % on weekdays, crossing the ~80 % tiering start point. NVMe consumed went from 0 GB to 20-35 GB, i.e. cold pages of the tiered VMs are now spilling to NVMe. Host active memory is 26-33 % of DRAM, still in the green <50 % recommended range, so the tiered VMs are not yet waiting on NVMe.

What to check next

  • Whether the 25 % DRAM reservation is acceptable for the remaining 41 tiered VMs and HA admission control DRAM tracking in 9.1.1.
