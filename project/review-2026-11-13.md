# Architecture review, 2026-11-13

Scope: Agent E2 as a whole: agent, harness, knowledge base, and the local model as far as it shapes them. Question asked: can this design reach the release gate on the next full run, and if not, what in the design stops it? Read only: no change, no new run. Not indexed.

- Fixed by the author, not reviewed: the mission; local, open-weight, no fine-tuning; "arrived" = the release gate (final score at least 85%, Level 400 at least 80%, confident-wrong at most 3%, each question on its worst of 5 runs); the next run is the full run.
- Two readings: this session, and an independent reviewer with no access to this session's conclusions. Where both agree, the finding says so. Every number was checked in the code or the saved data (verified) or follows from them (inferred).
- Evidence: the five run folders of 2026-11-12 and 2026-11-13 ([`benchmark/results/`](../benchmark/results)); the 20-question sample of 2026-11-13 (12 multiple choice, 8 judged, 2 runs, Gemma and Muse, up-front blocks and term map on); the code at `main`.

## 1. Verdict
- The architecture is sound. The knowledge base can answer: 149 of the 150 questions of the old runs got full credit in at least one run of some setup (only 0016 never did). The agent, the harness and the knowledge base need no rebuild. Both readings agree.
- The next full run will most likely not pass the gate. Projection for agentic mode as now configured: final score about 70-77%, Level 400 about 65-75%, confident-wrong about 5-10% (inferred from the sample, minus the drop from worst of 2 runs to worst of 5 seen in the full runs; the sample looks easier than the set, so this is optimistic).
- The root cause is not knowledge or retrieval. It is inconsistency: the same question gets different answers from run to run, and the gate scores the worst run. On judged questions the spread is large: credit on the best of 5 runs 0.72-0.89, on the worst of 5 runs 0.32-0.41 (every model, the frontier model included).
- Changed after this review (author, 2026-11-13): question credit is now the mean of the 5 runs, and each model runs with its own card settings (temperature 1.0). Sections 1 and 2 read the gate on the worst run, the rule at the time; on the old runs the mean is 16-20 points higher (Gemma agentic 72% against 54%, Muse 76% against 56%). Confident-wrong was already a mean per answer and is unchanged.
- Dropped by the author (2026-11-13): G4, pinning a gateway provider per model (irrelevant).
- Removed by the author (2026-11-13): the ceiling run (frontier model with the knowledge base). Agent E2 always runs on a local model, so that run measures nothing real.
- Two gate items are out of reach of every system measured so far, the frontier model included (section 2).

## 2. The gate against the data (both readings)
The run set: 196 questions, 119 multiple choice and 77 judged (39%). Level 400: 131, of which 59 judged (45%).

| Gate item | What it needs | Best measured (worst of 5 runs) |
|---|---|---|
| Final 85% | Judged credit at least 0.62, even with every multiple-choice question right ((0.85 - 119/196) / (77/196)) | 0.41 (Opus without the knowledge base); 0.40 (best classic); 0.34 (best agentic) |
| Level 400 80% | Judged Level 400 credit at least 0.56, multiple choice perfect | Below 0.41 |
| Confident-wrong 3% | At most 29 of the 980 answers (196 x 5) | Opus 10%; Opus with web 13%; agentic, old full runs, 22-28%; sample 5-10% on 40 answers (95% interval about 1-23%) |

- Why judged credit is low: the rubric scores 0 when one statement contradicts a key point ([`benchmark/runner/judge.py`](../benchmark/runner/judge.py), RUBRIC), and score 1 is almost never given (0.3-5% of judged answers). Zeros are a third of judged answers in every mode. In 73-86% of them the judge's own reason calls the answer partly correct (keyword count on the old judge's reasons).
- Why confident-wrong is high: a judged 0 not marked unsure counts as confident-wrong ([`benchmark/runner/run.py`](../benchmark/runner/run.py)). The judged half alone, at the sample rates (12-19%), gives 48-72 confident-wrong answers against the 29 allowed. Nothing makes the models abstain: Unsure is a prompt sentence ([`harness/modes.py`](../harness/modes.py)), and the candidates chose it on 0-1% of answers in knowledge base modes.
- Simulated on the saved answers (independent reading): a vote that turns disagreement into Unsure cuts confident-wrong by 1.5-5.6 points at no cost to the score; with a contradiction capped at 1 instead of 0 as well, confident-wrong is 4.7-10% and judged credit 0.42-0.53. Neither reaches the gate.

## 3. Findings on the design

### 3.1 The agent re-plans every run, and the worst run is scored (both readings)
- Temperature is 0.2 on every turn ([`benchmark/runner/config.yaml`](../benchmark/runner/config.yaml)), so the agent picks a different path in different runs. Overlap of the files read between runs: agentic 0.58-0.74, classic 0.95-0.96 (verified).
- On questions that flip, the worse runs read 7-20 points fewer needed files (verified). Agentic multiple choice: right in at least one run 94-97%, right in every run 67-72% (verified).
- Cost: going from the worst of 2 runs to the worst of 5 costs agentic 10-12 final points and classic 6-10 (inferred).
- The primed start (classic lookup first) made the path consistent (overlap 0.90) but the agent stopped calling tools and lost 10-22 points. Off, correctly.

### 3.2 The free-text path is the least built (both readings)
- Real use is free text, and judged questions carry the gate (section 2). The verifier and its repair turn run only on multiple-choice answers ([`harness/modes.py`](../harness/modes.py), [`harness/agent.py`](../harness/agent.py): `if kind == 'choice'`); a free-text answer leaves unchecked.
- Of the judged zeros in classic mode, 42-48% had every needed file in the context: the model added a sentence that contradicts the text it had.
- No change is proven to fix it. A grounding pass (check each claim against the files read) is the natural design, but it is not measured and could also remove correct claims.

### 3.3 Retrieval is not the limit (corrects the plan, decision of 2026-11-12)
- The plan read retrieval as the larger loss (59% of lost credit in answers with a missing file). Both readings now find that the content and retrieval can answer almost every question in some run; the loss is that they do not do it in every run.
- Budgets fit: needed files per question are 2.8K tokens median, 8.0K at most, against 12K of tool output; the largest single-turn prompt in the sample was 16.7K against the 32K window; no fallback in 2,410 agentic answers (verified).

### 3.5 Run-to-run noise the product will not have (this session; cause inferred)
- The gateway may serve an open-weight model from different providers (`varies_by_provider: true` for Gemma and Qwen). The runner pins none (`provider_order: {}`), and the `provider` column is empty in every run folder, so this noise cannot be measured afterwards. A local deployment runs one server.

## 4. Defects (verified)
1. The search-first rule fights the up-front blocks. The flow index, the procedure block and the term notes give file ids; the model reads one as its first action; the harness refuses it ("search first") and counts the refusal against the 8 calls. Gemma, cold start, sample: 46 refusals in 16 of 40 answers; 15 were reads of needed files. Cost about 1 point (inferred).
2. The letter parser misreads two answer forms ([`benchmark/runner/questions.py`](../benchmark/runner/questions.py), `parse`; the same pattern in [`harness/verify.py`](../harness/verify.py)): "ANSWER: C and E" reads as A, C, D, E (the letters of "and"); "ANSWER: **B**, **D**" reads as B. No sample answer used these forms: latent.
3. Classic mode searches with the shuffled options in the query ([`harness/modes.py`](../harness/modes.py), `classic_context`), so its context varies slightly between runs (overlap 0.95).
4. The `provider` column is never filled (3.5).
5. Stale documents: [`ARCHITECTURE.md`](../ARCHITECTURE.md) (the model "fits one GPU, at most 96 GB"; "Proof: shows that the product beats a frontier model"; term map in agentic mode "off until measured", it is on; the knowledge base "about 125K tokens", it is about 316K); [`harness/primer.py`](../harness/primer.py) docstring ("all off by default", all are on); [`benchmark/design.md`](../benchmark/design.md) sections 3.6, 4 and 7.5 sized for 150 questions, and section 13 still calls the screenshot questions deferred.
6. Question 0113: its key depends on Q192 (the `numa.autosize.once` default).

## 5. Keep as is (both readings)
- The three parts and their split: the agent chooses, the harness executes and constrains, the knowledge base speaks and wins.
- The knowledge structure (one object per metric file, same-name links, the Guest OS layer, the catalog, flows as numbered steps) and the retrieval.
- The exact tools (catalog, calculator, capacity plan, flow), the five up-front blocks (exactly at their 3,000-token limit), the term map, the format verifier with one repair turn, classic mode as control and fallback.
- Cold agentic start; reasoning off for Muse and Qwen with the preflight and health checks (with reasoning on, unreadable answers alone were 4.7% confident-wrong for Muse).
- The benchmark's fairness rules and the frontier reference as a user meets it.

## 6. Corrections to statements made earlier on 2026-11-13
- "The agent searches badly; this is the main lesson": confounded. The agentic runs of 2026-11-12 had the up-front blocks off; on the 13 sample questions also in those runs, Gemma agentic went from 66% to 87% (worst of 2 runs).
- "Reading the files it finds is the next lever" ([`harness/AGENT.md`](../harness/AGENT.md), section 6): weak support. In the sample, answers with full credit read about as many needed files as the others.
- The vote on multiple-choice answers (estimate: confident-wrong 9-18% to 1-7% on multiple choice) does not reach the gate: the judged half dominates confident-wrong.

## 7. Decisions for the author
| # | Decision | Why | Changes the product |
|---|---|---|---|
| G1 | What the full run decides, given section 2 | No measured system meets the judged-credit or the confident-wrong item. With the gate as it is, the run will report the distance, and 1.0 does not arrive on it | - |
| G2 | Temperature for the product, and so for the benchmark (the benchmark runs the deployed settings) | Inconsistency is the root cause (3.1); 0.2 is a choice, not a need. An expert answers the same question the same way. Effect at 0 not measured | Yes |
| G5 | Fix defects 1, 2 and 5; answer Q192 | Verified bugs and stale text | Defect 1 only, slightly |

- Not recommended before the full run: the vote, the grounding pass, any prompt change. None is shown to reach the gate, and each would enter the full run unmeasured.
- Challenge, for G1: a judged answer with one contradicting statement scores 0 and counts as confident-wrong, although in most cases the judge calls the rest correct. That is a strict reading of "an answer an operator would act on". It is the author's call; the data only show that, read this way, no system measured so far passes.
