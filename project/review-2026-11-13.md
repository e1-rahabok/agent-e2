# Architecture review, 2026-11-13

Scope: Agent E2 as a whole: agent, harness, knowledge base, and the local model as far as it shapes them. Question asked: can this design reach the release gate on the next full run, and if not, what in the design stops it? Read only: no change, no new run. Not indexed.

- Fixed by the author, not reviewed: the mission; local, open-weight, no fine-tuning; "arrived" = the release gate on the benchmark (final score at least 85%, Level 400 at least 80%, confident-wrong at most 3%, worst of 5 runs); the next run is the full run.
- Evidence: the five run folders of 2026-11-12 and 2026-11-13 (`benchmark/results/`), the 20-question sample of 2026-11-13 (plan, decision of that day), the code at `main` of 2026-11-13. Each finding says whether it was checked in the code or data (verified) or follows from them (inferred).

## 1. Verdict
- The architecture is sound. No finding calls for a rebuild of the agent, the harness or the knowledge base.
- The last full run did not measure the current design. The agentic runs of 2026-11-12 had the five up-front blocks and the term map off, Muse thinking and Qwen cut at the token cap. The current design is measured on 20 questions only. The next full run is its first real measurement.
- On the evidence, that run will most likely miss two gate items: confident-wrong and the final score. Both trace to one place: the free-text answer path (finding 2) and the lack of any abstention mechanism (finding 1).

## 2. Findings

### Finding 1. Confident-wrong has no mechanism behind it (verified)
- `ARCHITECTURE.md`, section 4, gives every model failure a mechanism in code or knowledge (catalog, calculator, flows, same-name links), except one: "Guesses when unsure" is answered by a prompt sentence only (Agent, prompt).
- The prompt sentence does not work on these models. Unsure chosen in knowledge base modes: 0-1% of answers (Gemma, Muse; old full runs and the sample). Opus without the knowledge base: 8%.
- Confident-wrong in knowledge base modes: 18-22% (old full runs), 5-18% (sample). Gate: 3%.
- Estimate from the saved runs (5 answers per question, read as 5 samples): answering a multiple-choice question only when 5 samples agree, and Unsure otherwise, keeps the multiple-choice score (Gemma classic 84%, Muse classic 81%, Muse agentic 72%) and lowers multiple-choice confident-wrong from 9-18% to 1-7%. The score does not drop because the worst-of-5 rule already gives 0 to a question whose runs disagree. Limits: the estimate reuses the same runs (optimistic); it covers multiple choice only.
- Design change, if wanted: a vote in the harness. Sample the final answer N times from the same context; answer when all agree, otherwise Unsure. Local cost: N completions per answer; the prompt is shared, so the time grows less than N times (inferred).

### Finding 2. The free-text answer path carries the gate, and it is the least built (verified)
- 77 of the 196 run questions (39%) are judged free text. Real use is free text too: an operator asks in a chat.
- Scores, knowledge base modes: multiple choice 92-100%, judged 58-75% (sample, worst of 2 runs); judged 32-40% (old full runs, worst of 5). Opus without the knowledge base: judged 41%.
- Arithmetic of the gate: with multiple choice at 90% on the worst of 5 runs, judged must reach 77% for a final score of 85% ((0.85 x 196 - 0.90 x 119) / 77).
- The harness checks only multiple-choice answers: the verifier and its repair turn run when `kind == 'choice'` (`harness/modes.py` line 186, `harness/agent.py` line 246). A free-text answer leaves unchecked.
- The judge rubric caps an answer at 0 when one statement contradicts a key point (`benchmark/runner/judge.py`, RUBRIC). Score 0 is about a third of judged answers in knowledge base modes (Gemma classic 97 of 300, Muse classic 90 of 300).
- Of those zeros, 42-48% had every needed file in the context (Gemma 41 of 97, Muse 43 of 90): the model wrote a sentence against the text it had. Sampled judge reasons read the same way: correct conclusion, then one added claim that contradicts the key ("claims that a power-off can change the vNUMA topology", "claims the guest link speed follows the physical vmnic").
- Design change, if wanted: a grounding pass on free-text answers. Before the answer leaves, the model checks each claim against the knowledge base text it read and removes or marks the claims that text does not support. One extra model turn. Not measured: its effect is inferred from the judge reasons, not shown.

### Finding 3. The proof has no control for a ceiling (verified)
- `benchmark/design.md`, section 7.5, defines a ceiling: the frontier model with the knowledge base, in agentic mode. It has never run, and it is not in the final round (`benchmark/runner/config.yaml`, `release.runs`: Opus in baseline and web only).
- Without it, a missed gate after the full run cannot be split between the local model and the rest (knowledge, keys, rubric). If the frontier model with the knowledge base also stays below 85%, the limit is not the local model.
- Change: add Opus in agentic mode to the full run. The preflight prices it.

### Finding 4. Run-to-run noise the product will not have (verified, cause inferred)
- The gateway can route each request of an open-weight model to a different provider (`varies_by_provider: true` for Gemma and Qwen in the run folders' `config.json`). A local deployment runs one server.
- The runner does not pin a provider (`provider_order: {}` in `config.yaml`), and the `provider` column is empty in every run folder, so the effect cannot be measured afterwards.
- The worst-of-5 rule turns any weaker serving into a lost question. The rule costs 10-18 points against the mean answer today (Gemma agentic: mean 72%, worst of 2 runs 64%, worst of 5 runs 54%). How much of that is provider routing is not known.
- Change: pin one provider per candidate model and record it. A setting, not a design change.

### Finding 5. The agent: no design change before the full run (verified)
- The conclusion of 2026-11-12, "the agent searches badly", was confounded by the blocks being off. On the 13 sample questions that were also in the old runs, worst of 2 runs, agentic mode: Gemma 66% to 87%, Muse 81% to 77%. On the 20-question sample, agentic is at or above classic for both models.
- The primed start failed (the agent stopped calling tools) and is off. Correct.
- Open gap: the agent sees needed files in search results that it does not read (Gemma 49% read against 64% seen; Muse 62% against 80%). A lever after the full run, not a blocker before it.

### Finding 6. Retrieval: known, not structural (verified)
- Classic context holds 75% of needed files; every needed file in about half the questions. The milestone is 90%. The retrieval check is paused by the author until the question revamp; the questions are now settled.
- The knowledge structure (one object per metric file, same-name links, layers) creates questions that need 2-4 files. That is the author's design and the reason the agent exists; it stays.

## 3. Defects (verified)
- `ARCHITECTURE.md` is stale in four places: lines 46 and 61 (the model "fits one GPU, at most 96 GB"; now a stretch target), line 47 ("Proof: shows that the product beats a frontier model"; the author's rule is that this is an outcome), line 171 (term map in agentic mode "off until measured"; it is on).
- Question 0113: its key depends on Q192 (the `numa.autosize.once` default). Until answered, a correct answer can score 0.
- The `provider` column is never filled (finding 4).

## 4. Keep as is
- The three parts and their split: the agent chooses, the harness executes and constrains, the knowledge base speaks and wins.
- The knowledge structure: one object per metric file, same-name links, the Guest OS as its own layer, the catalog for exact values, flows as numbered steps.
- The exact tools (catalog, calculator, capacity plan, flow), the five up-front blocks, the term map.
- Cold agentic start; classic mode as control and fallback.
- The benchmark rules: worst of 5 runs, the Unsure option, the fairness rules, the frontier reference as a user meets it (web mode).
