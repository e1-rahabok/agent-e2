# Holistic review of the repository, 2026-11-04

Not indexed. Scope: every file in the repository (209 knowledge files, 81,551 body words; 29 benchmark cases; docs; tools). Method: inventory of every file (title, size, headings, source, tags), automated duplicate and similarity checks across all knowledge files, then targeted reading of the overlapping groups. Proposed design: `docs/solution-design.md`.

## 1. Mission and framing
| Finding | Effect | Fix |
|---|---|---|
| README title and opening say "vSphere metrics knowledge base for AI". | The goal (a local 32B model beating frontier models, dark site) is not stated anywhere a reader lands. | New README opening (done in this change). |
| Scope stated as vSphere only. | Guest OS already exists; VCF Operations metrics are filed under vSphere; private cloud is the end scope. | Scope private cloud; vSphere 9.1 is version 1.0. |
| The harness (wrapper software) has no name and no home. Its prototype sits in `tools/autotest/`. | Readers see "a pile of markdown", not a system. | Name it the harness; give it its own folder. |
| No document explains to VMware professionals why a 32B model can win, or why these models. | The idea looks implausible to experts. | `docs/solution-design.md`, sections 3-5. |

## 2. Top-level structure
| Folder | What it actually holds | Problem | Proposal |
|---|---|---|---|
| `knowledge/` | What the model reads | Good, but mixes project config (allowed tag values in `glossary/terminology.md`) with knowledge | Keep; move tag config to tools |
| `docs/` | Design, decisions, author questions, to-do, 2 legacy files | Name suggests product documentation; overlaps with `knowledge/` in readers' minds | Rename `project/` |

| `tools/autotest/` | Benchmark runner and the harness prototype | GitHub shows a folder with one child as `tools/autotest`; there is no slash in the name. Two jobs in one folder | Split: `harness/` (retrieval, tool loop, prompts) and `benchmark/runner/` |

## 3. Knowledge structure
| Finding | Detail | Proposal |
|---|---|---|
| Three terminology places | `knowledge/foundations/terminology.md` (Allocation vs Reservation, Device vs Disk vs LUN, Usage vs Utilization), `knowledge/glossary/terminology.md` (synonyms, object types, proposed terms, words to avoid, allowed tag values), `knowledge/vsphere/glossary/logical-processor.md` (28 words) | One `knowledge/glossary.md` for the model; allowed tag values to `tools/` |
| `cluster-resource-management/` sits beside cpu, memory, storage | It is not a technology; it is a set of cluster features (DRS, DPM, shares, vCLS, admission control) | Fold into `vsphere/concepts/` (cluster topic) and `vsphere/objects/cluster/` |
| `system/` is a catch-all | Holds VCF Operations KPIs, capacity model, esxtop, GPU, BIOS, availability, sizing | Split by meaning: VCF Operations → `vcf-operations/`; esxtop → `vsphere/tools/esxtop/`; GPU stays a technology |
| VCF Operations metrics filed under vSphere | Contention, Net Run, Usage Disparity, Peak Core Usage, Cluster Performance/Risk/Consumption, VM Performance, capacity model, peak 20-second metrics: derived by VCF Operations, not vCenter counters | `knowledge/vcf-operations/`: separates raw counter from derived metric, a classic confusion (Contention vs Latency) |
| Technology-first metric folders | `vsphere/cpu/metrics/host/usage.md`: object is the third level | Object-first: `vsphere/objects/esxi-host/cpu/usage.md`. Users and VCF Operations start from the object; the id prefix in every chunk then leads with the vantage point |

| Images rule says `knowledge/vsphere/<technology>/images/` | Guest OS images now live in `knowledge/guest-os/<technology>/images/` | Rule: images next to the files that use them, per product folder |

## 4. Topic fragmentation (overlap by source, not by topic)
- 170 files come from the book, 29 from the Performance Best Practices PDF, 6 from the vSphere 9.1 documentation. Each extraction created its own files, so one topic is often split across 2-6 files written from different sources.
- Retrieval then returns partial files that each hold part of the answer, and occasionally disagree.
- Exact duplication is low (10 duplicated bullets, mostly the Guest OS Layer boilerplate); the problem is fragmentation.

| Topic | Files today | Proposal |
|---|---|---|
| Overhead | `vsphere/foundations/overhead`, `system/concepts/hypervisor-overhead`, `cpu/concepts/virtualization-overhead`, `memory/concepts/memory-overhead` | One overhead concept (classification, capacity), keep memory overhead detail as a child |
| Hyper-Threading and CPU accounting | `cpu-efficiency`, `esxi-thread-core-accounting`, `cpu-measurement-levels`, `hyper-threading`, `frequency-and-ht-impact-on-vm`, `cpu-capacity` | Three files: Hyper-Threading (scheduling and accounting), measurement levels and capacity, frequency |
| Memory reclamation | `overcommit-techniques` (PDF) vs `ballooning`, `swap-and-compression`, `page-sharing` (book) | Fold the PDF guidance into the book files |
| VM vs Guest OS boundary | `vm-vs-guest-os`, `visibility-layers` (+ per-technology `guest-os-vs-vm-*`) | Merge the two foundation files; keep the per-technology ones |
| Resource management | `vsphere/foundations/resource-management`, `cluster-resource-management/configuration/resource-settings-guidance`, `concepts/admission-control-and-cluster-state`, `concepts/scalable-shares` | One resource-management topic folder |
| Thresholds | `foundations/thresholds` (vendor-neutral), `vsphere-client-performance-guidance` (vendor values), thresholds inside metric files | Keep; feed all thresholds into the metric catalog with their source |
