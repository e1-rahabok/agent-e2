# Thresholds

Part of the knowledge rules; overview and why: [KNOWLEDGE-ENGINEERING.md](../../KNOWLEDGE-ENGINEERING.md). For writers and reviewers. Not indexed.

- A threshold has more parts than a number:

```text
threshold = (metric, object, instance reading, sample interval, time window) -> band values and source
```

- Sample interval: the same workload reads higher at 2 seconds (esxtop) than at 20 seconds, and higher at 20 seconds than at 5 minutes. A band set on 20-second peaks cannot be applied to a 5-minute chart. Example: VM Compressed + Swapped (5-minute samples) has a lower band than VM Memory Contention (20-second peaks) although it is the less serious signal.
- Instance reading: for a metric with instances (per vCPU, per disk), the worst instance is always at least the object value. The worst vCPU of a 64-vCPU VM can be far above the VM's normalized Ready. A band must say which reading it applies to, as "Peak CPU Ready among any vCPU" does.
- The name of a catalog row on a 20-second statistic says peak, and the name holds the scope: "Worst peak vCPU Ready among all VMs", "among VMs on the host". The same counter has other limits at 5 minutes than at a 20-second peak, and the worst VM of a cluster reads higher than one VM.
- One place per number. A number Agent E2 or a system decides with lives only in `knowledge/catalog/thresholds-*.yaml`; no knowledge file, table or image repeats it. A knowledge file holds the mechanism and the reasons, and numbers that no machine decides with: vendor values written as misconceptions ("the vendor says X; read Y"), reading rules ("Latency near 0 with Ready above 15% means a limit"), worked examples.
  - Admission: a row exists only for a use case: sub-metric limits of a KPI or model, score change, KAI or KSI, alert symptom, sizing range, capacity decision, or flow test (a number that one numbered step of a flow compares a reading with to pick the next step; Q-E2-195).
  - A KPI metric qualifies only if it maps to green, yellow, orange, red and a worse colour means slower work for the consumer. Banding alone is not enough: CPU Usage can be banded, but high usage is consumption, not slowness.
  - Sections are named by use, and the section name is the use: no `kind` or `use` field on the rows. The Harness labels every value with its use (KPI, Alert, Capacity decision, Capacity rule, Flow test), because one metric has a different threshold per use. Lint rejects any other section.
  - [`knowledge/catalog/thresholds-performance.yaml`](../../knowledge/catalog/thresholds-performance.yaml) (no SLA and no SLI: performance is managed by the KPI only):
    - `kpi`: the sub-metrics of the performance KPIs, one line per object and metric, five limits [best, green, yellow, orange, zero-at] for 5m, 20s and 2s (15 values): the values where the score is 100, 75, 50, 25 and 0; a limit is where a colour band ends; red is never open ended. One format for every scored line in the three files (`meta`, `limits_fields`), the adapter's model and terms (PCM-Adapter, docs/concepts/kpi-scoring-models.md). Entered by hand, null until entered, with `group`, `kb` and `excluded_when_green`. The 4x rule is a guide for choosing a 20-second value from a 5-minute one (a spike rarely lasts 300 seconds), not a formula: it never fills a cell. No class of service.
    - `change`: score change, one row per 0-100% score on a trend chart (a performance KPI, or a capacity model score read the same way): the smallest move from the median of the window, in points of the score, that counts as a drop or a rise (Q-E2-258: 5 points for the provider scores, cluster and host; Q-E2-259: 8 points for one VM's scores, VM Performance and Guest OS Performance). Fields as a flow row without `step`; `kb` is the file that explains the rule. Stage 3 reads it with the series a caller sends (`arithmetic_calculator.trend`). A score without a row gets its range only, never a verdict.
    - `flow`: flow tests, one row per number a flow step compares: `id` (flow-...), `metric`, `object`, `layer`, `interval` (only where a source states it), `operator` (one comparison, no range), `value`, `unit`, `meaning` (what the outcome means and the next step), `source`, `kb` (the flow file: troubleshooting, health check or decision tree) and `step` (its numbered step in `## Checks, in order`). Lint checks the step exists. While the step still writes the number in prose, the row carries a `quote` of that text. A flow test is not a KPI level and not an alert: the same metric can have a KPI line, an alert symptom and a flow test, each with its own value.
  - [`knowledge/catalog/thresholds-capacity.yaml`](../../knowledge/catalog/thresholds-capacity.yaml): `model` (the sub-metrics of Cluster Consumption) and `score` (the Cluster Consumption score), in the `kpi` line format; `sizing` (two-sided sizing ranges with grey for wastage: not scored); `decisions` (close for business); `rules` (planning and sizing).
  - [`knowledge/catalog/thresholds-risk.yaml`](../../knowledge/catalog/thresholds-risk.yaml): `model` (the sub-metrics of Cluster Risk) and `score` (the Cluster Risk score), in the `kpi` line format. A file of its own: Cluster Risk links performance and capacity.
  - [`knowledge/catalog/thresholds-alerts.yaml`](../../knowledge/catalog/thresholds-alerts.yaml): `symptoms`, one test each (object, metric, operator, value, unit; `role` gate for a filter such as CPU Usage above 1 GHz), written once; `alerts`, one definition per alert and criticality (`criticality`: red or orange, no yellow; `pillar`: performance or capacity), combining symptoms by id in `sets` (`relation` self or child with `population`; `match` all or any) with `wait_cycles`; one object type per alert. No free-text condition: every test is a symptom. Alerts are set apart from the KPI: different purpose, set separately.
  - Ids are unique across the three files. The Harness loads them into its catalog at start-up and shows a file's rows whenever the file is in Agent E2's reading set (catalog facts).
  - One name per sub-metric in Agent E2, PCM and the VCF vCommunity Adapter: the catalog name. The adapter shows the catalog name as its label and keeps its metric key, because a new key loses the metric's history and breaks the dashboards that read it.
  - The knowledge file a catalog line names in `kb` holds the line's name in its sub-metric table, so a sub-metric has one name in catalog and text. Lint fails when the name is missing.
  - Alert files hold no values: an alert's `kb` is its object type's alert file, which explains the alert under a `##` heading with the alert's `name`; a symptom's `kb` is the file of the metric it tests; no `quote`. Lint rejects a value (a number with %, ms, GHz, MB, IOPS, minutes or cycles) in a section named after an alert and in a misconception's correction. The one exception is a guide for an alert not in the set (datastore latency): no row holds it.
  - Still to move (a `quote` marks a row whose number is also in prose; lint checks the copy until it goes): decision tree steps (can-cluster-take-more-vms, host-cpu-capacity-headroom); class of service planning; monster VM sizes.
- No invented thresholds: a threshold goes in only with a source. Row field `source`: `knowledge-base`, or a vendor document with its version (`vsphere-9.1-docs`, `performance-best-practices-9.1`, `microsoft`), because vendor values can go stale and the newer official document wins.
- The rule for the model is in [`sp5-framework/observability/thresholds`](../../knowledge/sp5-framework/observability/thresholds.md) (Interval rule, Instance rule). The catalog has `interval` and `instance` fields, filled only where a source states them.
