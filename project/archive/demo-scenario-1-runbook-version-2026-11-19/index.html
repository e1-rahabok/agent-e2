Agent E2
▣ Computed by Agent E2 code (exact), not by the model
NVMe wait of VM = 6 MBps x 256 pages per MB x 290 µs / 8 vCPUs = 5.6% of its vCPU time.
arithmetic_calculator.py: NVMe wait (%) = VM NVMe read bandwidth (MB/s) x 256 pages per MB x host NVMe read latency (s) / VM vCPUs x 100 (Little's law). It assumes one 4 KB page per fetch and that the fetch stalls the vCPU; if either fails, it overstates the wait. Memory Contention does not count this wait. See vsphere/object-types/cluster/cluster-performance, section Sub-metric formulas.

VM Performance is low because the VM is waiting on NVMe fetches from memory tiering, which is scored in VM Performance but is not part of Memory Contention/CPU Ready.

VM Performance (%) aggregates contention sub-metrics, and for memory it uses peak memory wait plus NVMe wait on tiered hosts, vsphere/object-types/vm/vm-performance. VCF Operations Memory Contention maps to VM Memory Latency, vsphere/technology/memory/metrics/virtual-motherboard/latency. Latency measures vCPU wait for page faults – swap-in and decompression – and is unaware of memory tiering; on a tiered host it does not count NVMe fetches, vsphere/technology/memory/vm-memory-latency-high. The host-level ESXi Memory Latency is a normalized average of VM Memory Latency and hides the suffering VM; use the maximum VM Memory Contention instead, vsphere/technology/memory/metrics/host/latency.

With tiering on, host NVMe read latency 290 µs and VM NVMe read bandwidth 6 MBps on 8 vCPUs, NVMe wait ≈ 6×256×290µs/8 ≈5.6% of vCPU time per Little’s law, vsphere/object-types/cluster/cluster-performance. Balloon/compressed/swapped are 0 and peak Memory Contention 0.2% / CPU Ready 0.8% are near zero, so reclaim and CPU scheduling waits are absent; the NVMe wait is the component pulling VM Performance to ~17% today versus ~99% last week.

Check next: per-VM NVMe read bandwidth trend, host NVMe read latency baseline, active memory vs DRAM and tier in rate to confirm a working-set miss or warm-up, and Guest OS metrics to rule out in-guest wait.

NVMe read bandwidth 380 MBps at 09:10 and 360 MBps at 10:15, 65 minutes apart: above 200 MBps at the second reading: sustained: the working set no longer fits the DRAM left.
flow row flow-esxi-nvme-read-sustained: vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host, step 3

Conclusion: the NVMe reads are sustained, not a warm-up; the working set no longer fits the DRAM left on esxi-pay-05.

Mechanism and reason

  • Tiering is active: NVMe consumed is 0 GB until Friday morning, 50 GB at Friday 18:00 and 280 GB at Tuesday 08:00. Tiering starts once DRAM consumption passes ~80%.
  • Capacity signal: active memory is 790 GB at 09:10 and 785 GB at 10:15 on a 1,024 GB DRAM host ≈ 77% of DRAM. The decision tree for memory tiering uses Active memory as % of host DRAM: 50% or lower green, 50-75% at risk, >75% significant loss expected. Active is the capacity constraint on a tiered host, vsphere/technology/memory/metrics/virtual-motherboard/active.
  • Read bandwidth test: after an idle period pages that were not touched go cold to NVMe, so the first busy hour fetches them back. A warm-up falls back within the hour. The tree says: read NVMe read bandwidth again at least an hour after the first reading; at or ≤200 MB/s = warm-up; still >200 MB/s = sustained: the working set no longer fits the DRAM left. vsphere/technology/memory/decision-tree/is-memory-tiering-slowing-host

Here NVMe read bandwidth is 380 MBps at 09:10 and 360 MBps at 10:15, 65 min apart, both well above the 200 MB/s watch level. Computed: above 200 MBps at the second reading = sustained: the working set no longer fits the DRAM left.

  • Latency: NVMe read latency 290 µs / 280 µs is in the 200-400 µs potential-issues band. Each fetch costs ~1,000× a DRAM access and the vCPU waits for the fetch, vsphere/technology/memory/concepts/memory-tiering.

What to check next

Per-VM NVMe read bandwidth to identify which VMs are fetching, active memory per VM summed, and reclamation: balloon/compress/swap. Consider moving workloads off the host or lowering the DRAM:NVMe effective ratio, and review VMs that should not be tiered with a full reservation.

- Active memory: 785 GB (77% of DRAM).
- NVMe read bandwidth 360 MBps; NVMe read latency 280 µs.
- VMs: sql-pay-03 and 34 tiered VMs; 5 of them are payments application VMs (8 vCPU, 32 GB each).
VM sql-pay-03: 16 vCPU, 256 GB, sched.mem.enableTiering = "FALSE", memory reservation 256 GB (all of it), active memory 110 GB.

Agent E2

Conclusion: sql-pay-03 with tiering disabled and a full 256 GB reservation pins its memory in DRAM and reduces the DRAM that is left for the tiered VMs on esxi-pay-05, which is why the host is showing tiering-induced wait.

Mechanism and reason: on a memory-tiered host the capacity constraint is Active memory vs DRAM; Consumed may exceed DRAM by design. Tiering starts ~80 % DRAM and ages cold pages to NVMe. A VM with sched.mem.enableTiering = "FALSE" is excluded from tiering and must be fully reserved; otherwise its pages go to host swap. The full reservation makes the VM’s 256 GB plus per-VM overhead permanently resident in DRAM and non-reclaimable. Each DRAM-only reservation shrinks the DRAM left for tiered VMs, lowering the effective DRAM:NVMe ratio below the configured 1:1.

The host is in the tiering-slow zone: Active 785 GB = 77 % of 1,024 GB DRAM, above the 75 % threshold where significant loss is expected; NVMe read bandwidth 360 MBps >200 MB/s watch level and NVMe read latency 280 µs is in the 200-400 µs potential-issues band. VM Memory Latency / VCF Operations VM Memory Contention is unaware of memory tiering and does not count NVMe fetches; ESXi Memory Latency is an average that hides the worst VM. So low VM Memory Latency does not prove no wait. The peer hosts without the SQL VM are 44 %/41 % Active with ~30 MBps NVMe reads.

What to check next: per-VM NVMe read bandwidth for the 34 tiered VMs, especially the 5 payments VMs, and NVMe wait in Cluster Performance; host tier.consumed and per-VM tier1Consumed; reclamation balloon/compressed/swapped to rule out a non-tiered VM without a full reservation; and the DRAM left after reservations to compute the effective DRAM:NVMe ratio for the tiered workload.

Not settled by the knowledge base: the exact interval for the VCF Operations Active/NVMe metrics and the current tiered VM memory usage/placement on esxi-pay-05.

Capacity says the cluster has 30% memory left, but Highest ESXi DRAM Memory Consumed reads 108%. Which one is right?
📎 Readings attached (5 lines)
Attached from VCF Operations (selected by the user):
Cluster CL-SG-PRD-PAY: 8 identical hosts, each 1,024 GB DRAM plus a 1,024 GB NVMe memory tier (1:1); memory tiering configured since June; VCF 9.1.1 with the vCommunity management pack.
- Memory Capacity Remaining (%): 38 last Wednesday, 30 today. Time Remaining: over 200 days.
- Highest ESXi DRAM Memory Consumed (%): Monday 68, Wednesday 74, Friday 87, Tuesday (today) 108.
- Worst ESXi Active Memory, tiered hosts (% of DRAM): Monday 34, Wednesday 35, Friday 46, Tuesday 77.
- Worst ESXi NVMe Read Latency (µs): no reads on Monday and Wednesday, 120 on Friday, 290 today.
Agent E2

Capacity Remaining % is not the right headroom signal for a tiered cluster; Highest ESXi DRAM Memory Consumed % is the risk signal, and the active-memory / NVMe-latency pair is the performance signal.

Mechanism and reason

  • VCF Operations Capacity Remaining (%) is VCF Operations: usable capacity minus the highest projected utilization in the next 3 days, for the most constrained resource, a 3-day forecast against usable capacity. On a memory-tiered cluster VCF Operations is unaware of the NVMe tier and counts NVMe as part of Total Memory Capacity, so Capacity Remaining and Time Remaining treat NVMe as if it were DRAM and overstate supply. vcf-operations/features/capacity-forecast
  • Highest ESXi DRAM Memory Consumed is the Cluster Risk sub-metric DRAM Memory Consumed: memory consumed in DRAM and NVMe as % of host DRAM. On a tiered host it passes 100% by design; 157% means 1.57× DRAM is carried, the rest in NVMe. It is a leading indicator of risk, not contention. vsphere/object-types/cluster/models/cluster-risk
  • On a tiered host the capacity constraint moves from Consumed to Active memory. Consumed can exceed DRAM by design; Active must stay within DRAM, ideally <50% of it. vsphere/technology/memory/concepts/memory-tiering
  • Your data: Highest ESXi DRAM Memory Consumed 108% today means the worst host is already carrying 8% of its workload in the NVMe tier. Worst ESXi Active Memory 77% of DRAM is above the 75% point where significant performance loss is expected and well above the 50% green target. Worst ESXi NVMe Read Latency 290 µs is above the <200 µs good band and in the 200-400 µs potential-issues band. vsphere/technology/memory/concepts/memory-tiering

What to check next

Read active memory against DRAM and NVMe tier health, not Capacity Remaining. Check per-host Active % of DRAM, NVMe read bandwidth and latency, and tier consumed. If Active stays >50-75% of DRAM and NVMe read latency stays >200 µs, reduce workload on the hot host, avoid new reservations, and plan DRAM increase; NVMe is saturation, not free DRAM.
