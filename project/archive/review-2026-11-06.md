# Architecture review, 2026-11-06

Not indexed. A step back after a week of small changes: does each part serve the mission, what to change, what to retire. Nothing here is carried out until the author decides (section 8). The previous review: `project/review-2026-11-04.md`.

Mission: an open-weight model on one GPU, offline, answers Level 400 private cloud operations questions better than a frontier model.

## 1. Summary
1. **We stopped measuring.** No benchmark measured the system. Every change since the first version (prompt rule, catalog facts, verifier, up-front blocks, 73 new questions) is unmeasured. The next step is a benchmark run, not another structural change.
2. **Retrieval caps the system at about 70%.** Without a model, 72% of the files a question needs reach the classic context, and only 51 of 90 questions get every file. Embeddings add 1 point over keyword search. The misses are core concept files (Ready, VM vs Guest OS, memory latency), not stubs.
3. **The knowledge is broad on counters and thin on operations.** 109 of 206 files are metric meanings. Troubleshooting is 25% of the benchmark, but there are 12 short flows, only 1 has a diagram, and the first question an operator gets ("users say the VM is slow") has no triage flow. Capacity decisions are 20% of the benchmark and have no decision flow. VCF Operations, the tool operators work in, has 1 file of its own.
4. **No fact is reviewed.** 206 of 206 knowledge files are draft. Only Part 3 of the book is extracted; Part 1 (capacity and performance management) is not uploaded. The release gate needs reviewed content.
5. **The offline claim is untested.** No run on local weights, no context-window cap in the benchmark (the architecture says there is one; the code has none), no offline bundle, and the demo app does not call the harness.
6. **The documents drift because they repeat each other.** Rules live in [`CLAUDE.md`](../CLAUDE.md) and [`KNOWLEDGE-ENGINEERING.md`](../KNOWLEDGE-ENGINEERING.md); agent rules in [`ARCHITECTURE.md`](../ARCHITECTURE.md) and [`harness/AGENT.md`](../harness/AGENT.md); ingest rules in [`ARCHITECTURE.md`](../ARCHITECTURE.md) and [`KNOWLEDGE-ENGINEERING.md`](../KNOWLEDGE-ENGINEERING.md). `project/todo.md` has 107 open items, many pointing at paths that no longer exist. There is no single plan.

## 3. Mission review: what to improve
Ordered by expected effect on the score. Each item names its evidence and how we would know it worked.

### 3.1 Measure first
- Run the benchmark on the 66 scorable questions: 3 candidates and the frontier reference; baseline, classic and agentic; 5 runs. Dry-run estimate for the candidates: about US$ 19, plus the frontier model.
- Then, for the best candidate only, the up-front blocks one at a time and together (`--primer`).
- Why: without it we cannot tell which of the last week's changes helped. It also gives the first per-question picture for 49 new questions.
- Rule from now on: no structural change without a before and after number (benchmark or retrieval check).

### 3.2 Retrieval
- Evidence: the files missed most are the concept files a situation needs but does not name: `cpu/.../ready` (4 questions), `vm-vs-guest-os` (4), `memory/.../latency` (3), `cluster-sla-sli` (3), `capacity-model` (3). A question says "users complain, Ready is 2%"; it does not say "virtual motherboard".
- Cheap experiments, scored by the retrieval check in seconds, no model:
  1. Classic context: also expand `internal_derive` of the top hits (today only `same_name` and two `related`). Metric files point to their concepts there.
  2. Query expansion from the glossary: synonyms and confusable pairs (designed, never built).
  3. Route by question type: a troubleshooting question pulls the matching diagnosis file first (`retriever_guide: what-to-check`).
- Embeddings add 1 point. Either the embedding model is too small for this text, or chunks are too uniform. Test a larger local embedding model before relying on it.

### 3.3 Knowledge: depth where the questions are
Field view, from running large estates: what operators ask first is not "what does this counter mean". It is these:

| Operator question | Today | Proposal |
|---|---|---|
| Users say the VM is slow. Where do I start? | No triage flow. Per-resource flows exist but nothing chooses among them | Top-level triage flow: Guest OS or VM; which resource; then the per-resource flow |
| Can this cluster take N more VMs? When is it full? | Concepts exist (capacity model, Cluster Risk, HA headroom); no decision flow | Capacity decision flow ending in yes/no with the reason |
| Is this host or cluster healthy right now? | Overview files per object; no flow | Health check flow per object, contention first |
| Why is storage slow on this datastore? | 2 storage flows | Add datastore-level and vSAN flows when vSAN is in scope |
| Why are packets dropped? | 1 network flow (receive drops) | Transmit drops, physical NIC, vMotion network |

- Every flow gets a diagram for review; 11 of 12 have none.
- VCF Operations: operators work there daily, and a third of the screenshot questions show its UI. It has 1 file of its own. The VCF Operations 9.1 metric reference is not in the catalog. Needed: the author's VCF Operations chapters, and Part 1 of the book.
- Stubs: fill the 8 files under 60 words from the book, or fold each into its family file. They compete in retrieval and answer nothing.

## 5. Knowledge folder structure (Q3)
### Why it is this way
- The author's book reads metrics from three perspectives: technology, object, operations pillar. The folders follow the book: raw metrics by technology, derived content by object, cross-product pillars in `sp5-framework/`; tags carry the other perspectives (author, 2026-11-04).
- Object-first folders were proposed and declined twice (review 2026-11-04, decision 2).
- The model barely sees folders. Retrieval works on chunks, tags and links; the folder shows only in the id that prefixes each chunk, and in the agent's map. Folders matter for the author's review and for placement rules.

### Is there a better way?
- Not a re-organisation. The misses in 3.2 are not caused by folders, and a move costs every id, link, catalog row and question reference. Keep technology first.
- Three targeted fixes, where the current rules are broken or missing:

| Fix | Evidence | Proposal |
|---|---|---|
| VCF Operations content is filed under vSphere | The rule (CLAUDE.md, KNOWLEDGE-ENGINEERING.md section 8) puts what VCF Operations computes in `vcf-operations/`. But Cluster Performance, Cluster Risk, Cluster Consumption, Cluster SLA/SLI, VM Performance (vCommunity management pack KPIs), VM CPU Contention and the 20-second peak metrics sit under `vsphere/`, while `vcf-operations/` has 1 file | Move the derived metrics and KPIs to `vcf-operations/` (`metrics/`, `kpis/`), with `internal_derive` to the vSphere source counters |
| Tool references are scattered | `esxtop-cpu`, `esxtop-memory`, `esxtop-storage`, `esxtop-network` sit in each technology's `metrics/comparisons/`; [`vsphere/foundations/esxtop`](../knowledge/vsphere/tools/esxtop/overview.md) alone. Tool confusion is a trap type and a third of the questions are screenshots | One home per tool: `vsphere/tools/esxtop/`, `vsphere/tools/vsphere-client/`, later `vcf-operations/ui/`. The screen library (1.1) goes there too |
| No home for operations questions | Triage and capacity decision flows (3.3) cross technologies and objects | `sp5-framework/performance/diagnosis/` and `sp5-framework/capacity/diagnosis/`, as the layout rule already allows |

- Three foundation levels (`foundations/`, `vsphere/foundations/`, `sp5-framework/`) stay: different scope, and the rule is clear. `foundations/` is cited by 3 questions; fine for vendor-neutral content.
